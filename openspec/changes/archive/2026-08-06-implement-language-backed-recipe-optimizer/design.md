## Context

`pg-foma` already reifies compilation as a content-addressed Plan DAG, enumerates a default and a
small alternative set, filters candidates through the capability envelope, builds controllable
plans, compares them with the differential oracle, selects deterministically, profiles compilation,
and renders Plan JSON/Mermaid. The missing layer is a systematic way to derive realizable candidate
families from a new grammar and search them at a scale appropriate to the feasible space.

Two research notes supply the design basis:

- `docs/fst-plan/recipe-optimizer-literature.md` concludes there is no credible universal
  search-size threshold. Selection must use feasible-space size, constraint topology, measured
  evaluation cost, fidelity correlation, and the actual time/resource budget.
- `docs/fst-plan/linguistic-recipe-harvest.md` shows that actual constructions recur as a compact
  family of ordered cascades, partitions, templates, specialized branches, copy-handling branches,
  metathesis cascades, and morphological layers. Those are productive priors, not correctness
  evidence.

The production pipeline affected is the explicit offline/build-time path
`Grammar -> characterize -> enumerate/materialize Plan -> capability filter -> build/profile ->
full-HC confirm -> select/report`. Normal parse requests do not tune or mutate plans.

Ordering and ownership follow `openspec/changes/STAGING.md`. This change depends on
`reify-compilation-plans` and `visualize-compilation-plan`, consumes existing capability,
resource-safety, coverage, interaction, oracle, and profiling APIs, and does not take semantic
ownership of `replace.rs`, `gate.rs`, or `emit.rs`.

## Goals / Non-Goals

**Goals:**

- Convert grammar facts into an auditable, aggressively pruned recipe space.
- Start approximate, measure the problem actually presented, and adapt the algorithm as evidence
  accumulates.
- Make recipe families and search strategies independently extensible.
- Select only buildable, full-HC-conformant candidates and preserve analysis multiplicity.
- Produce enough evidence to reproduce a run and understand why a recipe won.
- Demonstrate at least two recipes on four promoted synthetic grammars where possible.

**Non-Goals:**

- Proving a universal optimizer threshold from literature.
- Using language identity, typology, or documentation as an admissibility or certification oracle.
- Changing HC semantics, Plan node kinds, or construct support.
- Runtime self-tuning, nondeterministic production selection, or weakening resource/recall gates.
- Claiming global optimality from a budget-limited run.

## Decisions

### D1. Separate syntactic, attested, static, and feasible spaces

The characterizer computes:

`N_syntactic`: all combinations expressible by registered family parameters;
`N_attested`: combinations generated by families with construction provenance;
`N_static`: candidates remaining after grammar dependencies, canonicalization, capability
predicates, and materializer preconditions; and
`N_feasible`: buildable candidates, exact when enumerated and otherwise an explicit estimate/bound.

Only executable grammar facts and compiler contracts are hard constraints. Linguistic provenance
controls generation order and ranking priors, preventing both arbitrary-tree explosion and
typology-based false pruning.

Alternative considered: search arbitrary Plan trees. Rejected because it spends nearly all work on
non-realizable or semantically meaningless shapes.

### D2. Registry entries are declarative envelopes around typed materializers

`RecipeFamily` contains a stable id/version, parameter domains, applicability predicate, dependency
emitter, prior, provenance, and a typed materializer returning a content-addressed `CandidatePlan`.
The schema is serializable for inspection; the Rust materializer is registered by id. Registry
validation rejects unknown versions, cyclic parameter dependencies, dangling references, and
missing materializers.

The first registry contains seven families named in the proposal. Families may share dimensions,
and canonical Plan identity deduplicates equivalent results across families.

Alternative considered: encode families directly in one enumerator match statement. Rejected
because each new construction would modify search logic and make provenance opaque.

### D3. Use a staged adaptive policy, with diverse beam as the first approximate default

Every run performs deterministic constraint propagation and a bounded pilot. It measures pruning
yield and p50/p95 costs for materialization, capability evaluation, build/profile, and available
low-fidelity scores.

The policy then chooses:

1. Exhaustive enumeration when `N_static * p95(full_evaluation) <= 0.5 * remaining_budget`.
2. Memoized dynamic programming when subproblems have compact reusable state and compositional cost.
3. Constraint programming / branch-and-bound when constraints prune strongly and useful admissible
   lower bounds exist.
4. Successive halving only when pilot data demonstrates that a cheaper fidelity predicts the final
   objective sufficiently well.
5. Constraint-guided diverse beam search otherwise.

V1 must implement exhaustive search, diverse beam, and one of memoized DP or branch-and-bound behind
a common interface. Beam diversity is by family and structural signature so a misleading early cost
estimate cannot collapse the run to one topology. Search is deterministic under an explicit seed.
The policy and thresholds are data, not scattered conditionals, so later calibration can change
them without changing family materializers.

Alternative considered: fixed thresholds based only on candidate count. Rejected because 50
million raw combinations may collapse to 50 thousand after pruning, and evaluation costs can differ
by orders of magnitude.

### D4. Evaluation is a cost ladder with a hard certification boundary

Candidates advance through: static admissibility; cheap structural estimate; capability envelope;
bounded build/profile; corpus evaluation; and full-HC confirmation. Earlier levels may eliminate
resource failures and rank survivors, but only the final level certifies analysis identity and
multiplicity. The current default candidate is always retained as baseline unless it itself fails
an existing hard gate.

All finalists are checked using the existing differential/full-HC oracle. Timeout, truncation,
unsupported behavior, or resource breach yields a typed non-certifying outcome. A candidate in that
state cannot be selected, regardless of speed.

Alternative considered: accept high sampled recall for selection. Rejected because rare negative
contexts and exception interactions are exactly where plausible recipes lose analyses.

### D5. Ranking is Pareto-first and deterministic

Confirmed candidates are compared on states, arcs, build time, apply time, proposals, and
confirmation work. The report retains the full Pareto frontier. The automatic winner is chosen
lexicographically by `(states + arcs, build time, apply time, proposals, confirmation work,
NodeId)`. Measurements include repetitions and quiet-machine metadata where required by staging.

This policy makes no claim that one scalar objective fits every deployment; callers can inspect the
frontier. V1 has one stable default policy so identical evidence produces an identical winner.

### D6. Reports are first-class evidence

`RecipeOptimizationReport` is schema-versioned canonical JSON. Markdown, candidate tables, and
Mermaid are derived views. It records hashes and versions, all space counts, pilot statistics,
chosen strategy and parameters, pruning reasons, every evaluated candidate and outcome, frontier,
winner, termination condition, and unexplored-space statement. Baseline and winner reuse
`plan_diagram` so diagrams describe executable Plans and real capability verdicts.

The four-grammar experiment is checked-in synthetic evidence. A combined deletion/reduplication/
exception fixture may be inspired by the Indonesian research case, but names and data remain
synthetic; the actual-language connection stays in comments and research documentation.

## Risks / Trade-offs

- **[Cost estimates mis-rank candidates]** → Keep family diversity, promote multiple finalists, and
  select only on measured, fully confirmed evidence.
- **[The registry encodes typological bias]** → Treat provenance as a prior only, permit generic
  baseline families, and report candidates excluded by each rule.
- **[Feasible counting is itself intractable]** → Use bounds/sampling with uncertainty and never
  label an estimated count exact.
- **[Successive halving discards late winners]** → Enable it only after measured fidelity
  correlation; otherwise use diverse beam.
- **[Benchmark noise changes ranking]** → Use deterministic structural tie-breaks, repetitions,
  quiet-machine metadata, and retain the Pareto frontier.
- **[A new materializer creates unsound Plans]** → Capability checks plus full-HC confirmation are
  mandatory; registry provenance never bypasses them.
- **[Search exhausts memory]** → Enforce logical candidate, build, elapsed, and memory budgets with
  typed termination and a complete partial report.

## Migration Plan

1. Land registry and characterization as read-only library APIs; existing enumeration/selection is
   unchanged.
2. Add optimizer strategies and reporting behind an explicit CLI command.
3. Run synthetic fixtures and the four-grammar experiment; the baseline remains the selected
   production behavior until a non-baseline candidate completes every gate.
4. Enable consumption of a saved winner only through an explicit, content-addressed artifact.
5. Roll back by ignoring/removing that artifact; `enumerate_default` remains available and no
   grammar or serialized HC data migration is required.

## Open Questions

- Calibrate the pilot sample size, beam width, and full-evaluation reserve from the first four
  grammar runs rather than guessing them in the design.
- Choose DP versus branch-and-bound for the third V1 strategy after characterization reveals whether
  compact reusable states or admissible bounds dominate the initial fixtures.
- Establish the measured fidelity-correlation threshold before enabling successive halving; it is
  disabled by default until then.
