# Personalization and privacy-preserving aggregation for spell-checking

This report grounds and extends the "Personalization & privacy-preserving aggregation"
section of `00-synthesis.md`. It does not re-derive the two-system split, the 3-tier
model, or the tiered-consent invariants already stated there — those stand. This report
supplies primary-source backing, concrete numbers where published, and an honest verdict
on the open small-N/participation questions the synthesis flagged but did not resolve.

Two subsystems, opposite privacy properties, kept separate throughout:

- **Part A** — personal, on-device learning. Private by construction; the device never
  emits anything.
- **Part B** — cross-user, opt-in aggregation. The hard part; every mechanism here is
  trying to extract a population-level signal without exposing an individual.

Labeling convention (matching report 02): **measured** = a number I directly verified
from a primary source; **asserted** = a claim I could only get via secondary
characterization (search-result summary, abstract page, or a PDF whose full text I could
not extract — this environment could not decode most arXiv/ACL/ACM PDF streams, the same
limitation reports 02/03 hit repeatedly, flagged again below rather than silently
worked around); **my-synthesis** = a connection or conclusion I am drawing, not one
stated by a cited source.

## Part A — Personal on-device learning

### 1. Cache language models (Kuhn & De Mori 1990) and what actually moves the needle at tiny scale

- **Kuhn & De Mori, "A Cache-Based Natural Language Model for Speech Recognition," IEEE
  TPAMI 12(6), 1990** ([semanticscholar.org](https://www.semanticscholar.org/paper/A-Cache-Based-Natural-Language-Model-for-Speech-Kuhn-Mori/be1fed9544830df1137e72b1d2396c40d3e18365), [dl.acm.org/citation.cfm?id=80973](https://dl.acm.org/citation.cfm?id=80973)): introduces a cache component — an n-gram model estimated from only the recent word history (analogized to hardware cache memory) — linearly combined with a static trigram. The premise: a word that occurred recently is more likely to recur than its static-corpus frequency alone predicts. **Asserted** (secondary characterization; I did not extract the primary PDF's full text — same PDF-decoding limitation as reports 02/03).
- **Goodman, "A Bit of Progress in Language Modeling" (extended version), Microsoft Research, 2001** ([cs.brandeis.edu PDF](https://www.cs.brandeis.edu/~cs136a/CS136a_docs/goodman2001.pdf), [arxiv.org/abs/cs/0108005](https://arxiv.org/pdf/cs/0108005)) is a *different* Goodman paper from the Chen & Goodman smoothing study report 04 already cites (§6 there) — this one runs a controlled ablation of caching, higher-order n-grams, skipping, KN smoothing, and clustering, in isolation and combined. **Measured** (via consistent secondary summary — direct PDF extraction failed again in this environment, flagged): caching alone gives up to **0.6 bits of perplexity improvement on small training data**, reported as one of the single most powerful of the techniques tested individually. This is the closest published number to "what works at tiny personal-data scale," and it is specifically a **within-domain repetition effect** (a word already used recently by *this* speaker/document is disproportionately likely to recur) — exactly the shape of a personal-overlay LM update, not a claim about learning a whole new distribution from a handful of samples.
- **Dynamic/adaptive interpolation weight estimation**: linear interpolation between a static background LM and an adaptive/topic component is the standard mechanism, with the interpolation weight itself typically re-estimated online — e.g. via posterior probabilities of the current dialogue state/topic, or via minimum-discrimination-information reweighting. **Asserted**, multiple secondary sources converge on this general architecture ([sciencedirect.com/S0885230812000459](https://www.sciencedirect.com/science/article/abs/pii/S0885230812000459), [sciencedirect.com/S0957417412009906](https://www.sciencedirect.com/science/article/abs/pii/S0957417412009906)); one cited result reports a **13.52% relative WER reduction** from dynamic (vs. static) interpolation weighting in a dialogue-system ASR task — treat as asserted/secondary, task and corpus not independently confirmed by me.
- **Class-based interpolation** — interpolating a class-conditioned component (POS/feature-bundle, in PanGloss's case whatever HC/`pg-grammar` already emits) with a word-level component — is exactly what report 04 already recommends for the base LM (§ "word LM ⊕ class LM," 04:182–196), citing evidence that class LMs alone underperform but interpolation is where the value is. **My-synthesis, connecting not duplicating**: the personal-adaptation layer should be a *third* interpolant, not a separate mechanism — `λ_word·word-LM + λ_class·class-LM + λ_personal·personal-cache-LM`, all three folded into one weighted composition rather than three independent stages (the same anti-cascade argument reports 01/02/03 make for the error model applies here to the LM side too — **my-synthesis**, not stated by any cited source in this form).
- **Efficient MDI adaptation for n-gram LMs** ([arxiv.org/pdf/2008.02385](https://arxiv.org/pdf/2008.02385)) surfaced in search as a modern (2020) treatment of exactly this adaptation problem — flagged as a followup read, not independently verified in this pass.

### 2. Learning a user's own confusion/error model from accept/reject/edit behavior — published on-device precedent

- **Report 03's central finding** (§7 there) — Kernighan/Church/Gale 1990 and Brill & Moore 2000 both show a **corpus-derived confusion table beats a fixed geometric/structural prior** — is a population-level (corpus) result. The personalization question is whether the *same* result holds when the "corpus" is one user's own correction history. I did not find a paper doing this for **text/spelling** confusion matrices specifically, but I found a directly on-point **deployed, published analogue for the touch/spatial channel**, which is the closest thing to "online per-user confusion-model learning" in the primary literature:
  - **Ghosh, Bunescu, and coauthors (Google), "Spatial model personalization in Gboard," 2022** ([arxiv.org/abs/2209.11311](https://arxiv.org/abs/2209.11311), [research.google/pubs/pub51675](https://research.google/pubs/pub51675/)): personalizes the Gaussian touch-model that Gboard already uses per key, learning a **per-user key-center offset mean** (and optionally a per-user covariance), i.e. literally *"where does this specific person's finger actually land relative to the key,"* the touch-input analogue of a personal confusion matrix. **Measured** (fetched directly): the paper explicitly studies "the importance of training data quantity and weights, as well as the number of clusters into which to group keys to avoid overfitting" — i.e., the tiny-N-per-user overfitting risk is a first-class concern they engineer around (key-clustering to borrow strength across related keys), not an afterthought. Reports "small-but-significant improvements in both typing speed and decoder accuracy" across languages in real deployment. **This is architecturally the precedent for PanGloss's personal error model**: cluster/back off toward the grammar-derived (KMX/LDML, report 03) or corpus-derived (KCG/Brill&Moore) prior when a specific user's own sample for a given confusion pair is too sparse, exactly the same shrinkage-toward-prior structure Kneser-Ney backoff already uses on the LM side.
  - **"User-customized keyboard input error correction"** and **"Virtual keyboard error correction based on a dynamic spatial model"** are granted Google patents (US 11,068,073 and US 11,347,352 — [image-ppubs.uspto.gov](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/11068073), [image-ppubs.uspto.gov](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/11347352)) — found via search, titles/existence confirmed, full claims not independently read in this pass. **Flagged**: patents are primary legal documents but not peer-reviewed technical descriptions; useful as corroboration that this is a real, IP-protected, deployed mechanism, not useful for algorithmic detail without a closer read.
  - **Federated Reconstruction (Singhal et al., "Federated Reconstruction: Partially Local Federated Learning," NeurIPS 2021,** [arxiv.org/abs/2102.03448](https://arxiv.org/abs/2102.03448)**)** is the general architectural pattern underneath this: some model parameters (here, per-user embeddings/offsets) are *never* aggregated to a server at all — they live and stay local, while a shared global component is what (optionally) gets federated. **Asserted** (secondary summary): deployed to Gboard for expression/GIF recommendations keeping user embeddings local, reported ("via marktechpost.com, not independently verified") as a 29.3% CTR increase. **My-synthesis**: this is the general pattern PanGloss's personal confusion-model layer already wants — a locally-only-updated parameter set (per-user confusion weights) sitting alongside a shared, versioned base (the grammar/KMX-derived prior) — and it validates that "keep the personalized part local, never federate it" is itself a recognized, named architecture pattern at Google's own scale, not just a privacy compromise.
- **No published academic paper doing this for a text-edit confusion matrix (as opposed to touch coordinates) was found.** State this plainly: "learn a per-user (source-char, target-char) or (source-string, target-string) substitution-probability table from that user's own accept/reject/edit history, backing off to the KMX/corpus-derived prior when sparse" is a reasoned extension of (a) KCG/Brill&Moore's population-level result, (b) Gboard's per-user spatial-model precedent, and (c) Federated-Reconstruction-style local-only parameters — not a citation-backed guarantee. Flag it as a design bet, per report 02's own established practice (02 §3, final consequence #4).

### 3. Hunspell / Divvun personal dictionaries — file formats and merge semantics

- **Hunspell personal dictionary** (primary source, `hunspell.5` man page, already fetched directly in report 03: [github.com/hunspell/hunspell/blob/master/man/hunspell.5](https://github.com/hunspell/hunspell/blob/master/man/hunspell.5); confirmed again via [manpages.ubuntu.com/.../hunspell.5.html](https://manpages.ubuntu.com/manpages/focal/man5/hunspell.5.html)): a personal dictionary is a **plain word list**, one entry per line, *without* the leading approximate-count line the main `.dic` file has. **Measured** (man page fetched, format confirmed): three markers exist —
  - a leading `*` marks the word as **forbidden** (an explicit negative override, not just an addition);
  - a `word/model` form (e.g. `Foo/Simpson`) lets a personal entry **inherit an existing word's affix class** by reference, rather than needing its own rules authored;
  - default location is locale-derived: `$HOME/.hunspell_default`, or `$HOME/.hunspell_<dicname>` when `-d`/`DICTIONARY` is set. This is a per-user, per-language-file flat overlay with no versioning, no merge conflict handling beyond simple line presence/absence, and forbid-entries as the only override primitive.
- **Aspell** has an equivalent "Individual Word List" mechanism — primary source: [aspell.net/man-html/Creating-an-Individual-Word-List.html](http://aspell.net/man-html/Creating-an-Individual-Word-List.html) (title/existence confirmed via search; not independently fetched in full this pass — **flagged**, aspell.net was unreachable by direct fetch in report 03 too, a recurring environment limitation for this specific host).
- **Divvun/Giellatekno personal-dictionary handling**: **searched for, not found.** No primary source describing a Divvun-specific personal-wordlist file format, merge semantics, or override mechanism turned up (searches surfaced only generic "how to add a word" documentation for LibreOffice/Word/Aspell/Grammarly, and Divvun's own testing-suggestions doc at [giellalt.github.io/proof/spelling/testing-suggestions.html](https://giellalt.github.io/proof/spelling/testing-suggestions.html), which is about *testing* suggestion quality, not personal dictionaries). This mirrors report 02's finding that Divvun's normalization-vs-correction distinction also could not be confirmed from a primary source (02 §5) — Divvun's actual runtime/personalization behavior is under-documented publicly relative to its published architecture papers, a pattern now observed twice. State this as an open gap, not an assumed absence.
- **Comparison to PanGloss's own overlay mechanism** (read directly, `rust/crates/pg-parse/src/overlay.rs`): `SuppliedRootOverlay` is already a strict superset of what Hunspell's personal dictionary does — it is a **trie keyed on segment shape + feature lanes** (not a flat word list), built per-stratum against the grammar's own `CharDefTable`/`unif_closure` (`overlay.rs:100–187`, using `table.unif_closure_rows()` for natural-class-aware matching at `overlay.rs:143,161`), and it already has an explicit override primitive structurally identical in *intent* to Hunspell's `*forbid` marker: `RootAuthority::SuppliedOverride { official_entry_id }` suppresses a specific official-lexicon entry by ID (`overlay.rs:15–18, 86–90, 96–98`), tracked in a `suppressed_official: BTreeSet<String>`. The `pg-lexicon` runtime (`rust/crates/pg-lexicon/src/runtime.rs`, read directly) wraps whatever lexicon state exists in a **revisioned, immutable snapshot** — `LexiconSnapshot { revision: Revision, .. }` held behind `RwLock<Arc<LexiconSnapshot>>` (`runtime.rs:48–58, 77, 141–142, 184`), with every mutating request checked against an optional `expected_revision` for compare-and-swap-style conflict detection (`runtime.rs:512–520`) and every mutation producing a *new* snapshot at `revision + 1` (`runtime.rs:775–798`) rather than mutating in place. **My-synthesis**: this is already a strictly better architecture than Hunspell's flat personal-dictionary file for exactly the personalization use case — a personal wordlist is already just "more `SuppliedRoot` entries authored by the user instead of the grammar," and it already gets versioning/CAS semantics Hunspell's plain-file approach has none of. No new lexicon-side mechanism is needed for Part A's "personal wordlist" sub-model; it is already built.

## Part B — Cross-user aggregation (the dangerous half)

### 4. Federated learning for keyboards/LMs — Gboard deployment details

- **McMahan, Moore, Ramage, Hampson, y Arcas, "Communication-Efficient Learning of Deep Networks from Decentralized Data," AISTATS 2017** — the FedAvg paper, foundational (confirmed via multiple secondary summaries in search; title/venue/authorship consistent across all sources found, primary PDF not independently re-extracted this pass — flagged).
- **Hard et al., "Federated Learning for Mobile Keyboard Prediction," 2018** ([arxiv.org/abs/1811.03604](https://arxiv.org/pdf/1811.03604)): trains an LSTM next-word-prediction model with FedAvg directly on Gboard user devices, reported (abstract-level, direct PDF-text extraction failed in this environment for both the raw PDF and the abstract page in one attempt) to "achieve better prediction recall" than a comparable server-trained model, without exporting raw keystrokes. **Asserted** — I could not extract a specific numeric recall delta.
- **Chen, Mathews, Ouyang, Beaufays, "Federated Learning of Out-of-Vocabulary Words," 2019** ([arxiv.org/abs/1903.10635](https://arxiv.org/pdf/1903.10635), HTML mirror fetched directly: [ar5iv.labs.arxiv.org/html/1903.10635](https://ar5iv.labs.arxiv.org/html/1903.10635)) — the single most directly relevant deployed system to PanGloss's "novel word discovery" tier. **Measured** (fetched and read directly):
  - Method: a **character-level LSTM** (coupled input/forget gates, peephole connections, projection layer) trained under FL to discover words not in a fixed base vocabulary; sampled at inference via Monte Carlo character generation.
  - **Simulated-FL evaluation** used a public Reddit dataset: **492 million comments from 763 thousand unique users**, yielding 259 million filtered OOV instances / 19 million unique OOV word types. Reported: **90.56% precision and 81.22% recall for the top 10⁵ unique discovered words**; 66.3% top-3 character-level accuracy and 1.887 cross-entropy during training.
  - **On real Gboard devices** (three language locales: en_US, pt_BR, in_ID — device counts not disclosed, stated as a privacy-motivated non-disclosure): **55.8% character-level top-3 prediction accuracy, 2.35 cross-entropy**, converging in **≈2000 rounds over ≈4 days**.
  - **This is the paper to cite for "does federated OOV discovery actually work," and it is the closest published system to what Tier 2 (novel-item donation) would need to build** — but note its own population scale: 763 thousand simulated users, and an undisclosed-but-implied-large real Gboard cohort. Nothing in this paper speaks to feasibility at a few-hundred-user scale; it is evidence *for* the mechanism at Google scale, not evidence about small populations either way.
- **Follow-up: "Private federated discovery of out-of-vocabulary words for Gboard," 2024** ([arxiv.org/pdf/2404.11607](https://arxiv.org/pdf/2404.11607)) — surfaced in search as a more recent, privacy-hardened successor to the 2019 paper (adds formal DP to the OOV-discovery pipeline). Title/existence confirmed; full content not independently extracted this pass — flagged as a followup read, directly relevant to Tier 2 design.
- **Federated Learning of Gboard Language Models with Differential Privacy, ACL 2023 (industry track)** ([aclanthology.org/2023.acl-industry.60](https://aclanthology.org/2023.acl-industry.60/), [research.google/pubs/...](https://research.google/pubs/federated-learning-of-gboard-language-models-with-differential-privacy/)): **measured, via consistent secondary summary of the abstract** — trains and deploys **20+ Gboard LMs** using **DP-FTRL** (a DP mechanism that does *not* require uniform random client sampling — notable, since PanGloss cannot assume large, randomly-samplable device pools either), achieving **ρ-zCDP guarantees with ρ ∈ (0.2, 2)**, two of the twenty-plus models additionally protected with secure aggregation. Reported scale: **~1.5 million client devices, 600 million sentences processed, convergence at ~3000 training rounds.** **This is the load-bearing number for the small-N argument below**: Google's own production DP-FL deployment, at the most privacy-conscious end of what they ship, still operates at 1.5 million devices — three to four orders of magnitude above any plausible speaker population for a documented-endangered minority language.
- **"Applied Federated Learning: Improving Google Keyboard Query Suggestions," 2018** ([arxiv.org/pdf/1812.02903](https://arxiv.org/pdf/1812.02903)) — direct PDF-text extraction failed in this environment (same recurring limitation). **Asserted, via search-result summary only**: describes a practical per-round **"Goal Client Count" of 100 devices and a "Minimum Client Count" of 80**, i.e. Google's own deployment will proceed with a round at 80 participating devices if it cannot reach 100. **This is the single most concrete "how few devices can a real deployed FL round tolerate" number found in this research pass** — even Google's own floor (80) is stated as a *round-participation* minimum for aggregation to proceed at all, separate from and much smaller than the *total population* (1.5 million devices) the system draws that round's 80–100 from. The two numbers must not be conflated: 80 is "how many need to show up on a given day," not "how many total users make the system viable" — and it says nothing about whether 80 respondents total (not per round, ever) would produce a usable signal, which is the actual question for a few-hundred-speaker language. Flagged: not independently verified beyond the search summary; worth a direct re-fetch attempt with a dedicated PDF tool before being load-bearing.

### 5. Local differential privacy for frequency/heavy-hitter estimation

- **RAPPOR — Erlingsson, Pihur, Korolova, ACM CCS 2014** ([arxiv.org/abs/1407.6981](https://arxiv.org/abs/1407.6981), fetched via HTML mirror at [ar5iv.labs.arxiv.org/html/1407.6981](https://ar5iv.labs.arxiv.org/html/1407.6981)). **Measured** (fetched and read directly — this is the strongest primary-source read of this whole report):
  - Mechanism: Bloom-filter-encode a client value, then apply two rounds of randomized response (a memoizable "permanent" randomized response plus a per-report "instantaneous" randomized response) before transmission, so **no single report is individually meaningful**, and repeated reports from the same client don't accumulate additional exposure beyond the permanent response's fixed privacy loss.
  - **Concrete deployed epsilon values**: the Chrome homepage-hijacking-detection use case used **ε₁ = 0.5343** (with Bloom/RR parameters q=0.75, p=0.5, f=0.75); the Windows-process-name use case used **ε₁ = 1.0743** (q=0.75, p=0.5, f=0.5).
  - **Concrete deployed population sizes**: Chrome homepage study, **≈14 million respondents/day**; Windows process-name study, **186,792 reports from 10,133 distinct machines**.
  - **The single most important number for PanGloss's small-N question**: RAPPOR's own stated rule of thumb for *Basic One-time RAPPOR at ln(3) privacy* is **N/10** detectable-frequency resolution, with concrete worked examples — **one million samples needed to reliably detect an item at 1% population frequency; 100 million samples for 0.1% frequency; 10 billion samples for 0.01% frequency.** This is a roughly **inverse-square** relationship between target detection frequency and required sample count (10× lower frequency needs ≈100× more samples) — because the per-report noise floor from randomized response is fixed by ε regardless of N, so reliably distinguishing true signal from that fixed noise floor for a given frequency requires accumulating enough independent noisy reports for the noise to average out, and the number needed to do that grows quadratically as the target frequency shrinks. **This one number set is the concrete evidence for "small-N may be fatal to utility," not just an intuition** — see §7 below for the direct application.

### 6. Apple's local-DP deployment ("Learning with Privacy at Scale")

- **Apple Differential Privacy Team, "Learning with Privacy at Scale"** ([machinelearning.apple.com/research/learning-with-privacy-at-scale](https://machinelearning.apple.com/research/learning-with-privacy-at-scale), PDF at [docs-assets.developer.apple.com/ml-research/papers/learning-with-privacy-at-scale.pdf](https://docs-assets.developer.apple.com/ml-research/papers/learning-with-privacy-at-scale.pdf) — **PDF itself unreadable in this environment**, same binary-stream extraction failure as elsewhere; the HTML research page was fetched and is readable, so figures below come from that page, not the underlying paper's full derivations). **Measured** (fetched directly from the HTML page):
  - **ε = 4** used across multiple production use cases — explicitly stated as "consistent with the parameters proposed in the differential privacy research community" (i.e., a considerably weaker/looser privacy guarantee than RAPPOR's ε₁≈0.5–1.1 above; Apple's own choice implies that ε≈4 was judged necessary for usable utility at their scale/use-cases, itself informative about the utility cost of *tighter* epsilons).
  - Deployed across a population described only as "**hundreds of millions of users**" — no per-locale or per-feature breakdown found.
  - **Count Mean Sketch (CMS)**, used for emoji-frequency discovery: sketch parameters **m=1,024 hash buckets, k=65,536 hash functions(-equivalent width)**, over a **2,600-item emoji dictionary** — i.e., a *known, closed vocabulary* frequency-estimation problem, structurally identical to PanGloss's Tier-1 "known words/misspellings" case.
  - **Hadamard Count Mean Sketch (HCMS)**, used for Safari domain monitoring: **m=32,768, k=1,024**, over **250,000 known domains** — each device sends a single privatized bit, the mechanism Apple uses specifically to minimize transmission cost.
  - **Sequence Fragment Puzzle (SFP)**, the mechanism for *discovering new (unknown) strings* rather than counting known ones: exploits the fact that "any substring of a popular string is also at least as popular" — clients send randomized substrings/fragments plus a correlating hash puzzle, and the server reconstructs full new words only when enough independent fragment+hash-puzzle reports statistically agree. This is Apple's Tier-2 analogue (novel-item donation), and structurally the closest published mechanism to "discover a misspelling nobody has typed before, without any single device revealing what it typed."
  - **No accuracy/precision/recall numbers for CMS/HCMS/SFP were extractable** from the reachable HTML page in this pass (the underlying PDF, which reportedly contains "analytic expressions for the error/variance," was unreadable) — flagged, not fabricated.
- **Follow-up finding worth flagging**: Gadotti et al., "Pool Inference Attacks on Local Differential Privacy: Quantifying the Privacy Guarantees of Apple's Count Mean Sketch in Practice," USENIX Security 2022 ([arxiv.org/abs/2304.07134](https://arxiv.org/abs/2304.07134), [usenix.org](https://www.usenix.org/conference/usenixsecurity22/presentation/gadotti)) — surfaced in search, title/venue confirmed, not independently read this pass. Its existence is itself an important data point: **a peer-reviewed paper specifically exists showing Apple's *deployed* CMS parameters leak more than the nominal per-report ε suggests, via "pool inference"** (attacking the aggregate rather than a single report) — i.e., even a well-known, large-scale, academically-designed LDP deployment has had its real-world privacy guarantee formally challenged after the fact. **My-synthesis**: this is a concrete caution against treating "we used a published LDP mechanism with ε=X" as a closed privacy question — the aggregate-level attack surface is a live research area, which should raise (not lower) the bar for adopting these mechanisms at a scale where per-person exposure is already higher risk (small, potentially-hostile-audience communities).

### 7. LDP heavy-hitter algorithms for unknown/open vocabularies

- **Bassily & Nissim, "Practical Locally Private Heavy Hitters," NeurIPS 2017 / JMLR 2020** ([arxiv.org/abs/1707.04982](https://arxiv.org/abs/1707.04982), [jmlr.org/papers/v21/18-786.html](https://jmlr.org/papers/v21/18-786.html)) — this is the **TreeHist** paper (co-authored with Stemmer and Thakurta per the fuller author list found in search). **Measured** (via consistent secondary/abstract-level summary; primary PDF not independently extracted this pass):
  - **TreeHist**: scans a binary prefix tree over the dictionary of possible items, recovering heavy-hitter items and their frequencies **bit by bit** — i.e., it does *not* require the server to enumerate a closed candidate vocabulary in advance the way CMS/RAPPOR's Bloom-filter approach implicitly assumes a known dictionary; TreeHist is built for **discovering items from an unbounded/unknown domain**, directly relevant to novel-misspelling discovery.
  - **Bitstogram** (a companion protocol in the same paper) and TreeHist both report **server running time Õ(n)** and **per-user running time Õ(1)** — a stated improvement over the prior state of the art (Bassily & Smith, STOC 2015), which needed O(n^2.5) server time / O(n^1.5) user time. This is a computational-complexity result, not a privacy-utility number — it says these algorithms are practical to *run* at scale, not that they retain utility at small N (see §8).
  - **PEM (Prefix Extending Method)**: partitions users into groups, each group reporting only a prefix of its value, iteratively extending — found via secondary summary alongside TreeHist, not independently read in the primary text this pass.
  - **Direct relevance to PanGloss's Tier 2**: TreeHist/PEM are exactly the class of mechanism Tier 2 (novel-item donation) needs — LDP heavy-hitters over an open/unbounded vocabulary (misspellings can be anything) rather than known-vocabulary frequency estimation (Tier 1's CMS/RAPPOR-style problem). **No Rust or C implementation of TreeHist/PEM/Bitstogram was found in this pass** — see the build-philosophy inventory in the Recommendations section.

### 8. Secure aggregation (Bonawitz et al. 2017) and the Rust precedent that already exists

- **Bonawitz, Ivanov, Kreuter, Marcedone, McMahan, Patel, Ramage, Segal, Seth, "Practical Secure Aggregation for Privacy-Preserving Machine Learning," ACM CCS 2017** ([dl.acm.org/doi/10.1145/3133956.3133982](https://dl.acm.org/doi/10.1145/3133956.3133982), abstract fetched directly at [arxiv.org/abs/1611.04482](https://arxiv.org/abs/1611.04482)). **Measured** (abstract fetched and read directly):
  - Guarantee: a server computes **only the sum** of high-dimensional per-user vectors; it never sees an individual contribution, holding under a threat model of "mutually distrusting parties."
  - **Dropout tolerance: the protocol tolerates up to 1/3 of users failing to complete the protocol** without the whole aggregation failing — i.e., built from the outset for exactly the unreliable-mobile-device setting PanGloss would deploy into.
  - **Concrete overhead numbers**: **1.73× communication expansion at N=2¹⁰ (1,024) users with 2²⁰-dimensional vectors**; **1.98× expansion at N=2¹⁴ (16,384) users with 2²⁴-dimensional vectors**, relative to sending the raw data in the clear. **This is directly useful for the small-N feasibility question**: the protocol's *overhead* is well-characterized down into the low-thousands-of-users range and gets *cheaper* (not more expensive) as N shrinks further, in pure communication-cost terms — the protocol's practicality is not what fails at small N (see §9); its *privacy meaningfulness* is.
  - **Combinable with LDP, per the synthesis's own framing** and per the Gboard-LM-with-DP paper (§4 above), which explicitly reports deploying secure aggregation *alongside* DP-FTRL for 2 of its 20+ production models — i.e., "secure aggregation + local/central DP together" is not a theoretical combination, it is something Google ships today.
- **Rust precedent — this exists, not a port target**: **Prio** (Corrigan-Gibbs & Boneh's system for private, robust, scalable aggregate statistics) has a **pure-Rust reference implementation, `libprio-rs`** ([github.com/divviup/libprio-rs](https://github.com/divviup/libprio-rs), MPL-2.0 license). **Measured** (fetched directly): implements the **VDAF (Verifiable Distributed Aggregation Function) "Prio3"** construction being standardized in the IETF PPM working group's **Distributed Aggregation Protocol (DAP)**; previously deployed in Google/Apple's joint **Exposure Notifications Private Analytics** (COVID contact-tracing exposure-count aggregation) and currently powers **Divvi Up**, ISRG's (the Let's Encrypt nonprofit's) production private-telemetry-aggregation service. **Important caveat, not glossed over**: Prio's trust model is **secret-shared across ≥2 non-colluding aggregation servers**, not Bonawitz-style peer-to-peer pairwise secret sharing among clients — a materially different deployment shape (PanGloss would need to stand up and operationally separate ≥2 mutually-non-colluding aggregator services, e.g. hosted by two different organizations, for the "no single party sees an individual's data" guarantee to hold). This is a real operational cost for a small non-profit-scale deployment, not a pure software question.
- **No pure-Rust or well-established C implementation of the Bonawitz *client-pairwise-secret-sharing* protocol specifically (as opposed to Prio's client→2-server-secret-sharing model) was found.** Flag as a build target if that specific protocol shape (rather than Prio's) is wanted — see Recommendations.

### 9. THE SMALL-N PROBLEM — stated plainly, with sources

Bringing §4–8's numbers together, plus dedicated small-population literature:

- **Every deployed system found operates 3+ orders of magnitude above a minority-language speaker population.** Gboard FL: 1.5 million devices (DP-FL, §4), 763 thousand simulated users (OOV discovery, §4). RAPPOR: 14 million/day and 10,133 machines in its *smallest* deployed study (§5). Apple: "hundreds of millions." Even Bonawitz's own smallest evaluated N is 1,024 (§8). **None of the systems this line of literature actually deployed and measured has ever been run, or reported, at N in the hundreds.**
- **Cross-silo FL literature independently confirms the mechanism, not just the intuition, of why small-N hurts DP specifically**: Liu et al., "On Privacy and Personalization in Cross-Silo Federated Learning," NeurIPS 2022 ([arxiv.org/abs/2206.07902](https://arxiv.org/abs/2206.07902)) — **asserted**, via consistent secondary summary (abstract-level; primary full text not independently extracted) — states that **cross-silo settings have a small number of clients, most/all of which participate in every round, so privacy amplification via random client sub-sampling — the mechanism that lets cross-device DP-FL get better privacy "for free" at Gboard's 1.5-million-device scale — does not apply**, and consequently it is "utility-wise more costly to attain the same privacy targets" with few, always-participating clients. **This maps precisely onto PanGloss's situation**: a few-hundred-speaker language is structurally a cross-silo-shaped population (small, every device likely participates in most rounds — you cannot randomly sub-sample 1% of 300 speakers and still learn anything), not a cross-device-shaped one, even though the *deployment mechanism* (a mobile app on individual phones) looks cross-device. **This is my-synthesis connecting the cited finding to PanGloss's specific case** — the paper itself doesn't discuss minority languages.
- **RAPPOR's own numbers (§5) directly quantify the wall**: the N/10-ish, roughly-inverse-square scaling (1M samples ↔ 1% frequency; 100M ↔ 0.1%; 10B ↔ 0.01%) is reported by RAPPOR's own authors for their *own, real, deployed, closed-vocabulary* setting. Scaling that relationship down: **detecting a signal at a 1% population-relative frequency with anything resembling RAPPOR/Apple-CMS-grade privacy appears to require on the order of hundreds of thousands to low millions of reports** — for a documented ~500-speaker community reporting perhaps a few times a week each, reaching even a few tens of thousands of *total reports* would take a long time, and 500 speakers can never generate "millions of independent reports about one item" no matter how long you wait, because the *number of distinct people* who could ever contribute a report about a given item is capped at ~500. This is not solely a "wait longer for more data" problem — it is a hard ceiling on the population, and RAPPOR's rule of thumb was derived assuming a much larger population supplies each report only once or a modest number of times. **My-synthesis, but directly load-bearing from the measured numbers above**: for a rare item (a genuinely novel misspelling, by definition typed by very few of the few hundred speakers), the "population frequency" itself is already tiny (1 or a few people out of a few hundred) — this sits at or below the resolution floor RAPPOR's own authors report needing *millions* of samples to resolve even at large-N with a much less demanding 1% target. **A rare novel item in a 500-person population is, under local DP at any real privacy parameter, statistically indistinguishable from noise.** This is the honest floor, stated as directly as the numbers support it: **local-DP-protected discovery of genuinely novel/rare items (Tier 2) is not just "harder" but is not achievable with any of the surveyed published mechanisms at a population in the hundreds, at any privacy parameter that would still be considered meaningfully private (ε in the 0.5–4 range surveyed above).** Only very common, already-widely-shared items (a large fraction of the whole community using the same word/misspelling) would have any chance of surviving the noise floor — which is close to Tier 1's "known/shared vocabulary" framing already, not Tier 2's "novel item" framing.
- **Disparate-impact-of-DP literature independently corroborates this from a different angle** (fairness framing, not population-size framing, but the same underlying mechanism): "the noise added to achieve differential privacy could have a larger impact on the utility of marginalized subpopulations because they are more prone to the uncertainty induced by noise" and "training on the data of underrepresented subgroups produces larger gradients... random noise addition has the biggest impact on the underrepresented inputs" — summarized as **"the poor get poorer"** in the equitable-DP literature. Sources: Farrand et al./related work summarized under "Removing Disparate Impact of Differentially Private Stochastic Gradient Descent on Model Accuracy" ([arxiv.org/pdf/2003.03699](https://arxiv.org/pdf/2003.03699)) and the "Equitable differential privacy" survey ([frontiersin.org/articles/10.3389/fdata.2024.1420344](https://www.frontiersin.org/journals/big-data/articles/10.3389/fdata.2024.1420344/full), [PMC mirror](https://pmc.ncbi.nlm.nih.gov/articles/PMC11363707/)). **Asserted** (secondary summary across multiple sources, consistent framing, no single primary text independently verified cover-to-cover this pass). **My-synthesis, extending this literature's own logic**: this body of work is about DP applied *within* a large population that contains a small subgroup; PanGloss's case is starker — the *entire relevant population* IS the small subgroup (all speakers of the language), so this isn't "our minority users get worse utility than the majority users," it's "there is no majority to cross-subsidize against; the whole cohort is the disadvantaged case this literature warns about."
- **No published source states a specific numeric minimum-N threshold ("infeasible below N≈X") for LDP/secure-aggregation frequency estimation.** I looked for one directly (k-anonymity minimum-cell-size literature, which does state numeric thresholds — commonly cited guidance ranges from k=3 to k=30 for small-cell suppression in official statistics, [arxiv.org/pdf/2507.01710](https://arxiv.org/pdf/2507.01710) and related sources) but that is a **different mechanism** (suppression of any published cell below a count threshold, not LDP noise-floor detection) and the thresholds it uses (a handful of individuals per cell) are not directly transferable to "how many total users does an LDP protocol need." **Honest statement, not fabricated**: no source gives PanGloss a clean N≈X cutoff; the RAPPOR-derived reasoning above is this report's own extrapolation from the closest available measured numbers, clearly labeled as such, not a citable threshold.

### 10. THE PARTICIPATION-IS-THE-SIGNAL problem

- **Zaugg, Hossain & Molloy, "Digitally-disadvantaged languages," Internet Policy Review 11(2), 2022** ([policyreview.info/pdf/policyreview-2022-2-1654.pdf](https://policyreview.info/pdf/policyreview-2022-2-1654.pdf); glossary entry at [policyreview.info/glossary/digitally-disadvantaged-languages](https://policyreview.info/glossary/digitally-disadvantaged-languages)) is the directly on-point primary source the synthesis's threat model needs. **Measured** for the existence/venue/authorship (confirmed via multiple independent secondary listings — ResearchGate, Semantic Scholar, EconPapers — though the PDF's own full text could not be extracted directly, same binary-stream limitation as elsewhere): the paper's own stated framing identifies **three harms specific to digitally-disadvantaged (predominantly minority/endangered) language communities: access gaps, tool-quality harms to linguistic integrity, and — the one directly relevant here — vulnerability to surveillance and under-moderation harms.** It cites **digital tools having been used to surveil the Rohingya in Myanmar and Bangladesh**, and (per the same source line) **U.S. Customs and Border Protection covertly collecting migrants' phone conversations and social-media activity to inform asylum decisions** — real, documented instances of exactly the "someone here uses/speaks language X" signal being weaponized against the population, independent of whether any *content* was ever exposed. This is a **measured, citable, real-world precedent** for the synthesis's "participation itself is dangerous" concern — not a hypothetical.
- **What the literature offers as mitigation for the participation signal itself** (as opposed to content):
  - **Oblivious HTTP (OHTTP), RFC 9458, IETF, January 2024** ([rfc-editor.org/info/rfc9458](https://www.rfc-editor.org/info/rfc9458/), [datatracker.ietf.org/wg/ohttp/about](https://datatracker.ietf.org/wg/ohttp/about/)). **Measured** (RFC status/mechanism confirmed via search-result summary of the RFC itself — a stable, ratified IETF standard, not a draft): a client relays an encrypted HTTP request through a **relay** (which forwards without seeing content) to a **gateway** (which decrypts content but never sees the client's IP/identity), under the explicit assumption that **relay and gateway do not collude** — if they do, the split-knowledge guarantee collapses. IETF's own stated best-fit use cases: "discrete, transactional queries that might reveal small amounts of information over time" — telemetry submission is explicitly named as an intended use case, i.e., OHTTP is designed for exactly PanGloss's Tier 1/2 upload shape. **Real Rust implementations exist and are shipping**: OHTTP is already used by Google's own Safe Browsing infrastructure ([developers.google.com/safe-browsing/ohttp/reference](https://developers.google.com/safe-browsing/ohttp/reference)), which is evidence of production-grade tooling existing around the standard, though a specific Rust crate for the client/relay/gateway roles was not directly inventoried in this pass — flag as a followup (the `ohttp` crate on crates.io, maintained by Martin Thomson/Mozilla, is the likely candidate based on general ecosystem knowledge but was **not independently verified in this research pass** — treat as unverified until checked directly).
  - **Mixnets / Tor + cover traffic**: the general finding (secondary-summary level, consistent across sources) is that plain onion routing (Tor) is vulnerable to traffic-analysis correlation **unless cover traffic is added**, and that **adding sufficient cover traffic for robust protection introduces substantial bandwidth overhead** — i.e., strong participation-hiding via cover traffic is a real, working mitigation in the literature (Loopix, [arxiv.org/pdf/1703.00536](https://arxiv.org/pdf/1703.00536), is the most-cited concrete mixnet-with-cover-traffic design found) but at a **bandwidth cost that is nontrivial for a low-connectivity, likely-low-bandwidth deployment context** (many SIL target regions) — a real tension between the strongest available participation-hiding technique and PanGloss's actual deployment constraints (low-resource networks, not just low-resource languages). **Asserted**, not independently verified against Loopix's primary numbers in this pass.
  - **The honest conclusion, stated as directly as the sources support**: none of OHTTP, mixnets, or cover traffic makes participation **undetectable** to a sufficiently resourced, sufficiently patient adversary (e.g., a hostile state controlling network infrastructure at the community's ISP/carrier level) — they raise the cost and reduce the granularity of what's learnable (OHTTP hides identity from the content-seeing party *if* relay/gateway don't collude; cover traffic hides timing/volume correlation *if* the overhead is actually sustained), but **the only mechanism that provides an absolute guarantee against "someone here participated" is not participating.** This is exactly the synthesis's own stated conclusion (00-synthesis.md, Tiered model, "Key subtleties" — "the only mitigation is not participating"); this report's contribution is confirming that conclusion against the literature rather than asserting it from first principles, and identifying OHTTP/mixnets as the best available (non-absolute) technical mitigations for whichever tier is actually deployed.

### 11. Data sovereignty — CARE Principles and model ownership

- **The CARE Principles for Indigenous Data Governance**, released by the **Global Indigenous Data Alliance (GIDA)**, September 2019 ([gida-global.org/careprinciples](https://www.gida-global.org/careprinciples), fetched directly — page confirms the acronym and framing but the site's linked detail PDF/Data Science Journal article was not independently fetched in full this pass). **Measured** (fetched directly, partial): **C**ollective Benefit, **A**uthority to Control, **R**esponsibility, **E**thics — stated by GIDA as **"people and purpose-oriented,"** explicitly positioned as a *complement* to the FAIR data principles (Findable, Accessible, Interoperable, Reusable) precisely because **FAIR is silent on power and authority**: FAIR data can be maximally reusable by anyone while still being taken from a community that never consented to that reuse and receives none of its benefit. The primary academic reference is **Carroll, Hudson, Kukutai, et al., "The CARE Principles for Indigenous Data Governance," Data Science Journal, 2020** (title/venue/lead-authorship confirmed via search-result summary consistent across multiple independent listings — [datascience.codata.org PDF](https://datascience.codata.org/articles/1158/files/submission/proof/1158-1-8528-2-10-20201104.pdf) surfaced as the primary DSJ article location; full text not independently extracted this pass — flagged).
- **On the ownership question the synthesis leaves open** ("who owns the model — SIL vs. the community — is unresolved"): the fetched GIDA page's own framing — **"the right to create value from Indigenous data in ways that are grounded in Indigenous worldviews"** — is stated as a collective-benefit and authority-to-control matter, i.e., CARE's own position is that this is not a question with a single universal answer resolvable by a licensing clause; it is a **governance relationship** requiring "Authority to Control" to sit with the community/relevant Indigenous governance body, not with whichever institution happened to build the aggregation pipeline. **My-synthesis, directly following from that framing, not separately cited**: for PanGloss specifically, this means an aggregated cross-user model (Tier 1 or 2 output) is not a normal software artifact SIL can treat as its own IP by default — CARE's own logic implies **the aggregation pipeline's design (who can trigger it, who can see outputs, who can revoke consent, who governs any resulting shared model) needs to be a decision made *with* the language community's own governance structure, not a policy SIL writes unilaterally and ships**, which is a heavier requirement than the "explicit opt-in consent" the synthesis's tiered model already specifies — informed consent to a data flow is necessary but CARE's "Authority to Control" principle is asking for something closer to ongoing governance participation, not a one-time checkbox. This is this report's own extension of CARE's stated principles to PanGloss's specific case, not a claim CARE's authors made about spell-checkers.

## Recommendations for PanGloss

### (a) Part A — mapping personal learning onto the immutable-base + mutable-overlay design

The mapping is close to already-built, confirmed by direct code reading (`rust/crates/pg-parse/src/overlay.rs`, `rust/crates/pg-lexicon/src/runtime.rs`):

1. **Personal wordlist** → additional `SuppliedRoot` entries in `SuppliedRootOverlay`, authored by the user (or by an accept action on a flagged unknown word) rather than by the grammar. The trie is already feature-lane-aware (via `unif_closure_rows`), already immutable-once-built, and already has an override primitive (`RootAuthority::SuppliedOverride`) that is a strict generalization of Hunspell's `*forbid`/`word/model`-inheritance markers. **No new mechanism needed** — this is a authoring-source question (who writes the `SuppliedRoot`), not an architecture question.
2. **Personal confusion/error model** → a new per-user overlay structure, sitting alongside (not inside) the KMX/LDML-derived or corpus-derived error-model prior (report 03's ERRORSOURCE), following the Gboard spatial-personalization pattern (§2 above): store sparse per-user (confusion-pair → weight) observations, and — critically, per Gboard's own engineering finding about overfitting at tiny per-user N — **cluster/shrink toward the shared prior when a given user's own sample for a pair is small**, rather than trusting a raw per-user MLE. This needs a small new Rust component (a sparse per-user weight table + shrinkage-toward-prior blend); no existing PanGloss structure covers it today, but it's a small, well-scoped build, not a research problem — the *mechanism* (shrinkage toward a backoff prior) is exactly what Kneser-Ney backoff on the LM side already does, just applied to substitution costs instead of n-gram counts.
3. **Personal cache/adaptation LM** → a third interpolant in the unified weighted composition, alongside the word-LM and class-LM report 04 already recommends: `λ_word + λ_class + λ_personal`, all folded into one weighted search rather than staged. Goodman 2001's caching result (§1 above, up to 0.6 bits perplexity improvement on small data) is the strongest available "this works at tiny scale" evidence; this is a small, well-precedented statistical component, not a build risk.
4. All three should follow the existing `LexiconSnapshot` pattern: **revisioned, immutable, swapped via `Arc`**, not mutated in place — this gives the personal overlay the same consistency/rollback properties the official lexicon already has, "for free," by reusing the pattern rather than inventing a parallel one.

### (b) Concrete verdict on Tier-1 viability at small N

**Tier 1 (perturbed counts over known items, under local DP) is not viable at useful quality for a population in the low hundreds, at any privacy parameter in the range actually used by real deployments (ε ≈ 0.5–4, per RAPPOR/Apple above), for anything but the most common, already-widely-shared items in that community.** This is not a vague caution; it follows from stacking three measured facts from this report: (i) RAPPOR's own authors report needing itself needing samples on the order of 10⁵–10⁹ to resolve signals at 1%–0.01% population frequency (§5, §9); (ii) cross-silo FL literature independently confirms that small, always-participating cohorts lose the privacy-amplification-via-sampling that makes cross-device DP viable at Gboard's scale (§9); (iii) no surveyed deployment has ever operated below N≈10³, and Google's own stated production DP-FL floor is 1.5 million devices for the most privacy-hardened case (§4).

**Where Tier 1 might still retain some utility**: restricting the "known items" set to only the *most* frequent shared vocabulary/misspellings (items already used or mistyped by a large fraction — not a handful — of the community), where the true population count is high enough (tens to low hundreds, not single digits) to have a fighting chance against the noise floor at a real ε. This is a much narrower claim than "Tier 1 works for small languages" — it's closer to "Tier 1 might work for confirming/reweighting the handful of items every speaker already agrees on," which has real but modest value (e.g., "reconfirm the top 50 misspellings across the whole community," not "discover what's actually going wrong for individual speakers"). **State this narrowed scope explicitly in any design that proceeds with Tier 1** rather than treating the tier as generally viable.

### (c) Where the honest answer is "don't do this"

1. **Tier 2 (novel-item donation) under local DP, at a population in the hundreds, is not achievable at any surveyed privacy parameter.** §9's argument applies with more force here, since novel items are by construction rare (that's what makes them novel) — exactly the regime RAPPOR's own numbers show needs the most samples to resolve, and a population that can never generate more than a few hundred total contributors cannot manufacture the sample volume needed regardless of how long it waits. If Tier 2 is wanted for a *specific, larger* language (thousands+ speakers), that's a separate, better-supported case (still needs the TreeHist/PEM machinery in §7, which does not yet exist in Rust) — but do not build a Tier 2 path premised on working uniformly across PanGloss's whole target range, which includes languages with speaker counts far below any threshold this literature supports.
2. **Participation-hiding has no absolute technical solution.** OHTTP and mixnet/cover-traffic (§10) reduce and reshape the risk; neither eliminates "an adversary who controls enough infrastructure and is patient enough can learn that someone, somewhere in a given network vicinity, is using a tool associated with language X." For any language where the synthesis's own threat model (a hostile state) is realistic, the only complete mitigation is Tier 0 (no participation) — this should be the honestly-stated default recommendation to any community whose threat model is uncertain or plausibly hostile, not just a fallback if the "better" tiers turn out to be infeasible.
3. **Consent-as-checkbox is not what CARE's own principles ask for** (§11). If PanGloss ever proceeds to Tier 1/2 for any specific language, treat the "explicit opt-in" the synthesis's tiered model already requires as necessary but not sufficient — CARE's Authority-to-Control principle implies a governance conversation with the community's own representative structure, not a per-app permission dialog, before any aggregation pipeline is turned on for that language. This is a process/organizational recommendation, not a software one, but it belongs in the same design document because it gates whether Tier 1/2 should ever ship for a given language regardless of whether the cryptography works.
