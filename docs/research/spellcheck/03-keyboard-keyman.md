# Keyboard-distance error models, and concrete Keyman integration, for spell-checking Phase 2

## Findings

### 1. How real spellers actually encode keyboard proximity, and its limits

- **Hunspell's `KEY` directive** (primary source, fetched directly: [github.com/hunspell/hunspell/blob/master/man/hunspell.5](https://github.com/hunspell/hunspell/blob/master/man/hunspell.5)): "Hunspell searches for and suggests words in which a single character has been replaced by a neighbouring KEY character." The format is literal same-row strings separated by `|`, e.g. `KEY qwertyuiop|asdfghjkl|zxcvbnm` or, for Dvorak, `KEY pyfgcrl|aeouidhtns|qjkxbmwvz`. This is exactly the "hardcoded coordinate/adjacency grid, one row-string per layout" design the plan's Phase 2 proposes — and it is Hunspell's own documented mechanism, not a strawman. **Its scope is narrow and explicit**: it is a *single-character-substitution* table only. It has no representation of diagonal/2D geometry (only same-row adjacency strings), no representation of shift-layer or dead-key input, and is authored per-*layout*, not per-*keyboard-driver-instance*.
- **Where `KEY` sits in the actual suggestion pipeline** (via Spylls, a from-source, tested reimplementation of Hunspell used as a primary-adjacent description of the original algorithm — [spylls.readthedocs.io/en/latest/hunspell/algo_suggest.html](https://spylls.readthedocs.io/en/latest/hunspell/algo_suggest.html)): the KEY-based substitution ("badcharkey": *"Try to replace chars by those close on keyboard ('wueue' -> 'queue')"*) runs **after** case-fixing, `REP`-table replacements, word-splitting, `MAP` mapping, and adjacent-swap edits, i.e. deep in a fixed cascade of structural-edit generators, all of which are checked against the dictionary directly (not scored against each other). Spylls' own commentary on the codebase does not defend this ordering as principled; it documents it as what Hunspell's C++ actually does. This corroborates report 02's independent finding (§6 there) that Hunspell's suggestion algorithm is a **cascade of incomparable-score stages**, not a unified weighted model — the keyboard-adjacency piece is one more ad hoc stage in that cascade, not a distinguished "prior" feeding a shared cost function.
- **Hunspell's `TRY` directive** is unrelated to geometry: it is just the language's alphabet ordered by letter frequency, used to generate every single-character substitution/insertion regardless of keyboard position — i.e., Hunspell's *primary* fallback for typo suggestion is a plain frequency-ordered brute-force alphabet scan, and `KEY` is a narrower, higher-priority special case layered on top of it, not a replacement for it. [github.com/hunspell/hunspell/blob/master/man/hunspell.5](https://github.com/hunspell/hunspell/blob/master/man/hunspell.5).
- **Hunspell's `PHONE` directive** borrows Aspell's phonetic table algorithm ("PHONE uses a table-driven phonetic transcription algorithm borrowed from Aspell... useful for languages whose orthography is not pronunciation-based") — same source. This is the phonetic-hash mechanism report 02 already covers in depth; noted here only to confirm Hunspell's own docs treat keyboard-adjacency and phonetic-similarity as two entirely separate, independently-authored tables, never combined into one cost.
- **Aspell** (primary source: [github.com/GNUAspell/aspell/blob/master/manual/aspell.texi](https://github.com/GNUAspell/aspell/blob/master/manual/aspell.texi), plus the `aspell.info` mirror at [github.com/mono/win32-installers](https://github.com/mono/win32-installers/blob/master/modules/gtk%2B-2.0-dev/sources/share/info/aspell.info)) uses a **separate keyboard-definition file** (`.kbd` extension) selected via a `keyboard` option with three presets: `standard` (QWERTY-like default), `dvorak`, and `none` (disables explicit keyboard layout entirely, i.e. Aspell itself treats "no geometric model" as a legitimate, supported configuration). Aspell's own manual frames its near-miss suggestion strategy as combining edit-distance (which folds in the keyboard-adjacency data) with Metaphone soundslike matching across graduated "suggestion modes" — e.g. "ultra" mode considers words "within one edit distance or have the same soundslike," "normal" mode expands to "soundslikes within two edit distance apart." This is a coarser but structurally similar cascade to Hunspell's: keyboard-adjacency data narrows which edit-distance-1 candidates are considered "cheap," phonetic matching is a parallel, separately-gated channel. I could not fetch the full "Notes on Typo-Analysis" section (the page that defines the `.kbd` file's own internal format) directly — `aspell.net` is unreachable in this environment (TLS certificate mismatch) and the GitHub mirrors of `aspell.info`/`aspell.texi` truncate before that section. **Flagged: the exact internal adjacency-table syntax of a `.kbd` file is asserted from secondary characterization, not independently verified by reading one.**
- **Divvun/Giellatekno's actual production speller architecture is a real-world precedent for the "unified weighted composition" report 02 already recommended, and is directly relevant to keyboard-distance too.** `divvunspell` ([github.com/divvun/divvunspell](https://github.com/divvun/divvunspell)) — a **Rust** reimplementation/extension of `hfst-ospell` — loads a ZHFST/BHFST archive containing two separately-authored weighted FSTs: a `LEXICON` (the morphological/word-form acceptor) and an `ERRORSOURCE` (error-model transducer), and runs the speller as "a composition of ERRORSOURCE and LEXICON" ([github.com/hfst/hfst-ospell](https://github.com/hfst/hfst-ospell), fetched directly). This is architecturally exactly the "one substitution-cost FST composed with the lexicon, not a staged fallback cascade" design report 02's synthesis argued for — and it already exists, in Rust, in a sibling SIL/UiT-language-tooling ecosystem. **I could not find or fetch documentation of *how* the ERRORSOURCE FST is itself authored** (i.e., whether keyboard-adjacency weights are hand-set, derived from a keyboard layout file, or learned from a corpus) — the hfst-ospell README documents the composition mechanism but not the error-model authoring process. **Flagged as an open sub-question**, not fabricated: divvunspell/hfst-ospell prove the *architecture* (weighted-FST composition of lexicon and error model) is real, deployed, and Rust-native, but do not by themselves prove keyboard-geometry-derived weights are what populates the error model in practice.
- **General pattern across all three systems**: none of Hunspell, Aspell, or Divvun's speller treats keyboard adjacency as *the* model — in every case it is one hand-authored table (or, in Divvun's case, one composable FST of unspecified provenance) feeding into, or run alongside, other signals. This partially validates the lead's framing: even the systems that *do* hardcode a geometric table never treat that table as sufient on its own, and Aspell explicitly supports disabling it (`keyboard=none`).

### 2. Keyman file formats and where the keystroke→output mapping actually lives

*(Primary sources: keymanapp/keyman is MIT-licensed, copyright SIL Global 2017–2025 — [github.com/keymanapp/keyman/blob/master/LICENSE.md](https://github.com/keymanapp/keyman/blob/master/LICENSE.md), fetched directly.)*

- **`.kmn`** — plain-text keyboard *source*. Confirmed by direct fetch of [help.keyman.com/developer/language/guide/overview](https://help.keyman.com/developer/language/guide/overview): "The Keyman language is a language designed around **transforming inputs to outputs, through rules rather than through static tables**." A `.kmn` file is a sequence of `rule`, `comment`, `store`, `group`, or `header` lines. This is a direct, primary-source rebuttal of the plan's framing that keyboard behavior is naturally table-shaped — Keyman's own design philosophy is explicitly rule-based, not table-based, precisely because output depends on context (preceding characters, preceding dead-key state), not just the current keystroke.
- **`.kmx` / `.kmx+`** — the *compiled* binary keyboard, and where keystroke→output mapping is actually stored. Primary source, fetched directly: [github.com/keymanapp/keyman/blob/master/docs/file-formats/kmx-file-format.md](https://github.com/keymanapp/keyman/blob/master/docs/file-formats/kmx-file-format.md). Structure: a `KXTS`-magic header (`COMP_KEYBOARD`) references an array of **groups** (`COMP_GROUP`), each holding an array of **keys** (`COMP_KEY`) — each key rule records the virtual key, modifier flags, an *output* offset, and a *context* offset (i.e., the rule fires only in a given preceding-character context, exactly matching the `.kmn` rule-context model). **Dead keys are not a distinct structure**; they're represented through the general **store** system, same as any other named buffer. Newer keyboards may carry an optional `KMX+` block (flagged via `KF_KMXPLUS`) alongside the classic format — documented separately at [github.com/keymanapp/keyman/blob/master/docs/file-formats/kmx-plus-file-format.md](https://github.com/keymanapp/keyman/blob/master/docs/file-formats/kmx-plus-file-format.md), fetched directly. This confirms: **the keystroke→output mapping is a group/key/rule graph with context, not a flat lookup table** — a single physical keystroke's output is a function of engine state, not a static per-key value.
- **`.kmp`** — the distributable *package* (a zip-like bundle of one or more compiled keyboards plus metadata, fonts, docs, welcome screens) per [help.keyman.com/developer/current-version/reference/file-types/kmp](https://help.keyman.com/developer/current-version/reference/file-types/kmp) (title/summary confirmed via search; not independently fetched in full).
- **`.kvk` / `.kvks`** — the **On-Screen Keyboard**, a *separate* artifact from the hardware `.kmx`. Primary source, fetched directly: [help.keyman.com/developer/language/reference/visualkeyboard](https://help.keyman.com/developer/language/reference/visualkeyboard). `.kvks` is the XML source (UTF-8, edited in Keyman Developer's Keyboard Editor); `.kvk` is its legacy compiled binary form, referenced from the `&visualkeyboard` system store. I could **not** fetch the .kvks XML schema itself in enough detail to describe its row/key/width structure directly — the reference page I could reach ([help.keyman.com/developer/current-version/reference/file-types/kvks](https://help.keyman.com/developer/current-version/reference/file-types/kvks)) states only that it is "a Keyman On Screen Keyboard source file... XML format with UTF-8 encoding," without exposing the schema. **Flagged: exact .kvks internal geometry fields not independently verified**, though its purpose (a distinct visual/spatial artifact from `.kmx`) is confirmed.
- **A *third*, separate touch-layout format exists**: `.keyman-touch-layout`, a JSON file referenced by the `&layoutfile` system store, used specifically on touch platforms (mobileWeb/iOS/Android), taking priority over `.kvk`/`.kvks` when present. Primary source, fetched directly: [help.keyman.com/developer/language/reference/layoutfile](https://help.keyman.com/developer/language/reference/layoutfile). Critically, its own docs state: **if neither `&layoutfile` nor `&visualkeyboard` is specified, "Keyman automatically generates a touch layout based on the US English desktop keyboard layout."** This is a directly load-bearing finding for the lead's challenge: **a large fraction of real-world Keyman keyboards for minority/indigenous languages may have no custom touch geometry at all** — their on-screen key arrangement silently defaults to US-English QWERTY regardless of the target script, meaning any geometry-derived confusion model for touch input must check, per keyboard, whether a genuine custom touch layout exists before trusting its geometry — otherwise it's measuring confusability against a layout the target-language typist never actually sees/uses in the intended script.
- **`.keyboard_info`** — pure *metadata*, not mapping data. Primary source (JSON schema): [api.keyman.com/schemas/keyboard_info.schema.json](https://api.keyman.com/schemas/keyboard_info.schema.json) (schema URL confirmed via search of [help.keyman.com/developer/cloud/keyboard_info/current-version/](https://help.keyman.com/developer/cloud/keyboard_info/current-version/)). Fields include `id`, `name`, `authorName`, `license`, `version`, a `platformSupport` object (per-platform: `full`/`basic`/`dictionary`/`none`), a `languages` object keyed by BCP-47 code, font/OSK-font references, and an `examples` array of sample keystroke-sequence → output-text pairs. **It explicitly does not contain the keystroke-to-output mapping itself** — that logic lives only in the compiled `.kmx`/`.js`. The `examples` array is the closest thing to ground-truth confusability data Keyman ships as metadata, but it is a tiny illustrative set, not an exhaustive table.

### 3. Dead keys, `store()`, rule contexts, `begin Unicode` — one grapheme, many keystrokes

*(Primary sources, all fetched directly from help.keyman.com/developer/language/reference/.)*

- **`store()`** ([.../reference/store](https://help.keyman.com/developer/language/reference/store)) creates a named buffer — of characters, virtual keys, `deadkey()` markers, or `outs()` output strings — reused across rules via `any()`/`index()`/`outs()`. Stores are the general mechanism; dead keys are just one kind of content a store can hold.
- **`deadkey()`** ([.../reference/deadkey](https://help.keyman.com/developer/language/reference/deadkey)) "emits an invisible placeholder in the output, or matches an invisible placeholder in the context." A rule like `dk(backquote) + 'e' > 'è'` fires only when the backquote-deadkey marker precedes the keystroke `'e'`, and a separate rule `+ '\`' > dk(backquote)` is what produces that marker from the actual backtick keystroke. **This is the direct, primary-source confirmation of the lead's central claim**: producing `è` here is a **two-keystroke sequence** (backtick, then e) mapped through an **intermediate invisible state marker**, not a single keystroke mapped to a single character. Any per-character geometric distance model has no way to represent "the cost of mistyping the *second* keystroke of a dead-key sequence" or "the cost of omitting the dead-key keystroke entirely" — both are extremely common real typing errors in dead-key-heavy orthographies, and both are keystroke-sequence-level events, invisible at the character level.
- **`begin Unicode`** ([.../reference/begin](https://help.keyman.com/developer/language/reference/begin)) is simply the standard modern entry point for Unicode-aware processing (superseding the deprecated legacy `ANSI` entry point) — it dispatches to a named rule group. Not itself a source of adjacency data, but it confirms every compiled keyboard's behavior is entered through a **rule-dispatch graph**, reinforcing that "the output for keystroke X" is not a static fact independent of what has already been typed.

### 4. On-Screen Keyboard / touch layouts vs. hardware layouts: confirmed separate geometry, and what geometry data actually exists

- Keyman maintains **at least three distinct on-screen/touch layout formats** (`.kvk`/`.kvks`, `.keyman-touch-layout` JSON, and — per §6 below — LDML `keyboard3` touch `<layers formId="touch">`), each independent of the `.kmx` hardware rule graph, confirmed across the sources in §2–§3 above. This directly validates the lead's framing: **hardware and touch are separately-authored geometries in Keyman's own architecture**, not one geometric fact with two renderings.
- Where geometry data *does* exist in Keyman's newer format, it is **relative, not Euclidean/coordinate-based**. In the `KMX+` `layr` (layers) section, a key's `width` field is documented as "key width\*10 (supports 0.1 as min width)" — a scalar multiplier of a base key unit, not an `[x, y]` coordinate — and layout selection across device sizes uses a scalar `minDeviceWidth` in millimeters, not a 2D grid ([github.com/keymanapp/keyman/blob/master/docs/file-formats/kmx-plus-file-format.md](https://github.com/keymanapp/keyman/blob/master/docs/file-formats/kmx-plus-file-format.md), fetched directly, cross-referencing UTS #35 §7 for full semantics). **There is no `[f32; 2]`-style absolute coordinate anywhere in Keyman's own on-disk formats** — row-relative key width/order is the actual representation, which is a materially different (and weaker, but real) geometric signal than the plan's proposed hardcoded grid.
- Physical/hardware key *position* (as opposed to touch key width/order) is represented differently again: via **scan codes** and an ISO row/column position convention (rows lettered A–E, columns numbered), confirmed in both the LDML spec (§6) and referenced by KMX+'s hardware-layout linkage. This is a third geometry vocabulary, again not `[f32;2]` coordinates but discrete row/column labels.

### 5. Deriving a keystroke-level confusion/adjacency model from an installed Keyman keyboard: what's possible today

- **The KMX/KMX+ binary format is fully, openly documented** (MIT-licensed spec files directly in the `keyman` repo, §2 above), and **reference parsers already exist** as shipped tooling rather than something PanGloss would have to reverse-engineer: the `@keymanapp/kmc-kmn` compiler (source→`.kmx`), `@keymanapp/common-types` (shared TypeScript type definitions for these formats), and — most directly relevant — **`@keymanapp/kmc-analyze`**, an existing static-analysis package whose documented job is exactly "analyze a keyboard file... to produce a [derived artifact]" (its shipped subcommand `kmc analyze osk-char-use` scans one or more compiled keyboards and produces a `&displayMap` file) (confirmed via search of [github.com/keymanapp/keyman/blob/master/docs/npm-packages.md](https://github.com/keymanapp/keyman/blob/master/docs/npm-packages.md) and related help pages; **I was not able to fetch kmc-analyze's own README/source in full — the specific subcommand and its stated purpose are as reported in Keyman's own documentation search results, not independently read from the analyzer's source**). This establishes **precedent**: Keyman's own tooling already does static analysis over compiled keyboards to derive secondary artifacts. A "derive a keystroke confusion table from a compiled keyboard" tool would be a new `kmc analyze` subcommand in the same spirit as `osk-char-use`, not a novel integration pattern.
- **There is no ready-made "confusion matrix" or "adjacency" export today.** Checked directly: the `.keyboard_info` schema (§2) explicitly does not carry mapping data; the Keyman **Core** engine's C API ([help.keyman.com/developer/core/desktop/current-version/](https://help.keyman.com/developer/core/desktop/current-version/), fetched directly) exposes a stateless keystroke **Processor** (feed one virtual-key+modifier event, get back "Actions" describing how to transform the text buffer) plus state get/set and "query calls to return static attributes data for keyboards and engine" — but its own docs describe this API as "intended for use only within Keyman Engine," and its JSON introspection schema ([help.keyman.com/developer/core/11.0/json-schema](https://help.keyman.com/developer/core/11.0/json-schema), fetched directly) is explicitly documented as "intended solely for use in diagnostics or by development and debugging tools," not a stable public contract, and does not expose per-rule keystroke→output data (the `rules` field in the introspection JSON is present but undocumented/empty in the schema as published). **There is no built-in "enumerate every keystroke sequence this keyboard can produce" call.**
- **Two concrete, source-grounded paths exist to build one anyway:**
  1. **Static parse of the compiled `.kmx`/`.kmx+`** — walk the documented group/key/store graph directly (per the open binary spec in §2) and enumerate, for each virtual-key+modifier+context combination, the output string it produces. This is a batch/offline analysis, matching the `kmc-analyze` precedent, and does not require driving the live engine.
  2. **Drive the stateless Core `Processor` exhaustively** — since the engine documents itself as stateless with respect to keyboard state (state lives in the client), one could programmatically feed every virtual-key/modifier/prior-context combination through the C API and record the resulting Actions, effectively black-box-enumerating the keyboard's keystroke→output relation without parsing `.kmx` internals at all. This is more robust to `.kmx`/`KMX+`/(future) LDML format differences, since it goes through Keyman's own execution semantics rather than a hand-rolled binary parser, but is not a documented/supported usage of an API that its own docs say is "intended for use only within Keyman Engine."
  - **Neither path is a documented, off-the-shelf Keyman feature today; both are buildable using only primary, openly-licensed artifacts (the MIT-licensed `.kmx` spec, or the MIT-licensed Core engine's own C API).** This should be stated as **synthesis/recommendation, not existing tooling** — I found no evidence anyone has already built this.

### 6. LDML / CLDR keyboards (UTS #35 Part 7) — the right cross-keyboard interchange format, with caveats

*(Primary source, fetched directly: [unicode-org.github.io/cldr/ldml/tr35-keyboards.html](https://unicode-org.github.io/cldr/ldml/tr35-keyboards.html); an older public-review copy at [unicode.org/reports/tr35/tr35-49/tr35-keyboards.html](https://www.unicode.org/reports/tr35/tr35-49/tr35-keyboards.html) was also fetched and is consistent.)*

- **Structure**: a keyboard is defined by a locale-named layout file (e.g. `en-t-k0-osx.xml`) plus a shared `_platform.xml` file. The platform file's `hardwareMap` maps raw OS keycodes to **ISO layout positions** (row letters A–E, column numbers 00–12) — i.e., LDML deliberately separates *physical key identity* (ISO position) from *what a given OS reports for that key* (raw keycode) from *what character that position produces* (the layout file's `<map>` elements per modifier-combination `<keyMap>`). `<transform>` elements encode dead-key/multi-keystroke sequences generically (e.g. caret dead-key + `e` → `ê`) via **markers**, described as "placeholders which record some state, but without producing normal visible text output... designed particularly to support dead-keys" — the same conceptual mechanism as Keyman's `deadkey()`, now standardized. Touch layouts are a first-class, separate `<layers formId="touch">` construct, with relative (not absolute) `width` per key and a `minDeviceWidth`-in-mm selector across device-size variants, plus a `longPress` attribute for the (mobile-specific) sustained-press alternate-character behavior.
- **Explicitly confirmed: LDML keyboards has no adjacency/error-modeling concept at all.** Direct search of the spec text for "adjacent," "proximity," "distance," "error" turned up nothing relevant — the spec's scope is strictly the *functional* input→output mapping (which keystroke sequence produces which text), not any notion of confusability or geometric closeness between positions. **This means LDML is a source you derive an adjacency prior *from* (via its ISO position graph or touch layer key-order), not a place a prior is already published.**
- **Keyman is actively adopting LDML as its "Keyboard 3.0" strategy, not treating it as a competing format** — confirmed by both [keyman.com/ldml/](https://keyman.com/ldml/) (fetched directly) and the Unicode blog's own account of the effort ([blog.unicode.org/2023/05/ldml-uts35-part-7-keyboards.html](http://blog.unicode.org/2023/05/ldml-uts35-part-7-keyboards.html), fetched directly, explicitly framed as solving fragmentation: *"every platform must independently evaluate, prioritize, and implement all new or updated keyboard layouts, leading to major inconsistencies and delays especially where digitally disadvantaged languages are concerned"* — language directly on-point for PanGloss's target population). Status as of the fetch (dated within the page as of December 2025 / a February 2025 note on the current site): **Keyman 17.0 already supports LDML keyboards on Windows/macOS/Linux desktop**; web/iOS/Android LDML support and a visual editor are in development, targeted for Keyman Developer 19.0. Existing `.kmn` keyboards are unaffected and continue to be supported — LDML is additive, not a forced migration. There is also `@keymanapp/kmc-ldml`, a compiler package for LDML sources alongside `@keymanapp/kmc-kmn` for classic `.kmn` sources ([github.com/keymanapp/keyman/blob/master/docs/npm-packages.md](https://github.com/keymanapp/keyman/blob/master/docs/npm-packages.md), fetched directly).
- **Practical implication for "which format should PanGloss's parser target"**: because LDML is one spec with one parser needed (versus KMX's binary-per-legacy-format plus a forthcoming KMX+ variant plus eventual LDML-native compiled forms), and because Keyman itself is converging on it as the long-term interchange format specifically to solve the fragmentation problem SIL/Keyman's own target population (under-resourced languages) suffers most from, **LDML `keyboard3` XML is the more future-proof format to build a keystroke-adjacency derivation tool against** — but **today**, most deployed field-language keyboards are still `.kmn`/`.kmx`-only (LDML desktop support only shipped in Keyman 17.0, and mobile/web support — the platforms most field typists actually use — is still in development as of this research). A real integration needs to handle **both** for the next several years, not choose one and ignore the other.

### 7. Observed confusion matrices vs. geometric priors — what the noisy-channel literature actually argues

- **Kernighan, Church & Gale, "A Spelling Correction Program Based on a Noisy Channel Model," COLING 1990** ([aclanthology.org/C90-2036](https://aclanthology.org/C90-2036/)): the paper's own program, `correct`, ranks single-edit-distance candidate corrections by `Pr(c)·Pr(t|c)` where `Pr(t|c)` — the channel/error model — is built from **confusion tables of insertion, deletion, substitution, and transposition counts** (i.e., counted from actual correction data), not from keyboard-geometry distance. **I was unable to extract the primary PDF's full text directly** (the fetch returned undecodable compressed binary content, consistent with the same PDF-extraction limitation report 02 hit repeatedly) — the summary above is corroborated across multiple independent secondary sources (ACL Anthology's own listing, dblp, Semantic Scholar's indexing) describing the paper's stated method, but **flagged as not independently verified against the primary full text by me**. The key point for this report, however, is uncontroversial across every secondary description found: **the seminal noisy-channel spelling-correction paper's error model is a corpus-derived confusion table, not a geometric prior.** Geometric keyboard distance is not mentioned as the error source at all in any description of this paper found.
- **Brill & Moore, "An Improved Error Model for Noisy Channel Spelling Correction," ACL 2000** ([aclanthology.org/P00-1037](https://aclanthology.org/P00-1037/)): generalizes Kernighan/Church/Gale's single-character-edit confusion table to **arbitrary-length string-to-string substitutions `α→β` with probabilities estimated from a large corpus of real (misspelling, correction) pairs**, explicitly framed by the paper (per ACL Anthology's own listing and the paper's abstract as indexed by ACM DL — [dl.acm.org/doi/10.3115/1075218.1075255](https://dl.acm.org/doi/10.3115/1075218.1075255)) as a "significant improvement" over prior single-edit noisy-channel models. **Same PDF-extraction limitation applies** — both direct fetch attempts (ACL Anthology PDF and a Semantic Scholar mirror) returned unreadable compressed binary or empty content; the description above is from consistent ACL Anthology/ACM/dblp secondary characterization of the paper's own stated contribution, not independently verified by me against the full primary text. **This is the single most directly on-point piece of literature for the lead's challenge**: it is a widely-cited, foundational result that **learned, corpus-derived substitution probabilities beat a fixed structural/geometric edit model**, for exactly the class of problem ("what character/string did the typist probably mean to produce") that keyboard-distance modeling is trying to solve. Report 02 (§6, §3 there) already independently surfaces this paper as the precedent for "fold everything into one weighted channel model rather than staged fallback cascades" — this report corroborates that the same paper is *also* the direct precedent against hardcoding geometry as the substitution-cost source.
- **Divvun/Giellatekno and Hunspell/Aspell's own designs (§1) are consistent with, not contradicting, this literature**: none of them claim geometric adjacency alone is sufficient — Hunspell layers `KEY` under `TRY`-alphabet-scan and whole-dictionary n-gram fallback; Aspell layers `.kbd` edit-distance under Metaphone soundslike matching and lets users disable the keyboard model entirely (`keyboard=none`); Divvun's ERRORSOURCE-FST-composed-with-LEXICON architecture is structurally exactly what a learned (or at minimum, richer-than-single-character) substitution model would want to plug into. **No system surveyed treats a hardcoded coordinate grid as the primary or sole error signal** — it is, at best, one coarse structural-edit generator among several, in every real system found.

### 8. Touch / fat-finger models

- **Goodman et al.'s probabilistic touch-keyboard model** (found only via secondary characterization in search results, not independently fetched from a specific primary paper — flagged): described as fitting "a multivariate Gaussian distribution to hits over a given key," combined with a language model in a speech-recognition-style decoder, replacing rigid key-boundary assumptions with a continuous probability surface over tap location; reported (again, secondary-summary-only) to reduce error rates by "a factor of 1.67 to 1.87" versus a naive nearest-key model. **I could not locate and independently fetch Goodman et al.'s original paper/venue in this pass** — treat the specific numbers as asserted-via-secondary-summary, not verified.

## Recommendations for PanGloss

**Verdict: the lead's challenge is well-founded and corroborated by every primary and secondary source found. Drop the hardcoded `[f32; 2]` QWERTY/AZERTY grid. The confusable unit for a Keyman-typed language is the keystroke sequence realized through that specific installed keyboard's own rule graph, not the character, and the noisy-channel literature's own central finding (Brill & Moore 2000 over Kernighan/Church/Gale 1990) is that a corpus/keyboard-derived cost beats an assumed structural one even for plain hardware typos.**

1. **Do not hardcode per-language keyboard layouts inside PanGloss.** Every real system surveyed that uses a geometric adjacency table (Hunspell `KEY`, Aspell `.kbd`) authors it *per keyboard layout*, as a small, swappable, external artifact — never compiled into the core engine. For PanGloss's actual deployment context (SIL field languages, typed through Keyman keyboards that are frequently language-specific, dead-key-heavy, and different across desktop vs. mobile), a fixed QWERTY/AZERTY grid would be actively wrong for a large fraction of real input — both because the physical layout in use is often neither (many Keyman keyboards remap keys entirely for the target orthography) and because, per §4, **a meaningful fraction of touch keyboards silently default to the US-English layout's touch geometry** even when the hardware/intended layout is completely different, which a hardcoded QWERTY/AZERTY-only grid would not model either.

2. **The confusable unit must be the keystroke sequence, not the character — this is not just the lead's intuition, it is what Keyman's own architecture forces.** §3 shows a single output grapheme can require an arbitrary number of keystrokes through `deadkey()` markers and rule contexts; §6 shows LDML standardizes the identical concept (`<transform>` + markers) industry-wide. A per-character `[f32;2]` grid has no representation for "typist pressed the base key but forgot the preceding dead key," "typist's dead-key press itself was mistyped," or "typist used the wrong modifier layer" — all of which are keystroke-sequence-level events that collapse to the *same* output character as a correct sequence, or produce a *different* character than intended, in ways invisible to character-level geometry. Any keyboard-cost model needs to operate over **(keystroke, modifier, prior-marker-state) → output** relations, matching the actual `.kmx`/LDML rule-graph structure, not over a character alphabet.

3. **Treat geometry as a weak, swappable *prior* feeding one unified weighted-edit-cost function — not a separate hardcoded stage.** This is both report 02's independent architectural recommendation (§6 there) and the central, repeated finding of the noisy-channel literature surveyed here (§7): Kernighan/Church/Gale's original confusion tables and Brill & Moore's generalized string-substitution model were both **learned from data**, and Brill & Moore's whole contribution was demonstrating that a data-derived model beats a fixed structural one. Concretely: keyboard cost should be one more weighted-substitution-cost source composed into the same lexicon-FST search that Phase 1 (deletion transducer) and the revised Phase 3 (feature-lane phonological cost, per report 02) already use — exactly the divvunspell/hfst-ospell pattern of `ERRORSOURCE ⊗ LEXICON` composition (§1), and exactly the shape of Google's FST-based touch-decoder architecture (§8), even though this report could not independently verify that paper's numbers.

4. **Concrete answer to "how do we connect to Keyman": ingest the actual installed/target keyboard's own compiled artifact, not a generic layout name.** Two artifacts to consume, per keyboard, both MIT-licensed and openly specified:
   - **Hardware**: parse the compiled `.kmx`/`.kmx+` (or, increasingly, the LDML `keyboard3` + `_platform.xml` pair once a given keyboard has migrated — Keyman 17.0+ desktop already supports this) to recover (a) the actual virtual-key/modifier/context → output rule graph (§2–§3), and (b) the physical key-adjacency graph via ISO row/column position + scan codes (§6). Compose these two into a keystroke-sequence-level confusion prior: two output events are "geometrically confusable" if their generating keystroke sequences differ by a small edit *in the physical key-position graph*, which is a keyboard-specific, not assumed-QWERTY, geometry.
   - **Touch**: separately parse whichever of `.kvks`/`.kvk`, `.keyman-touch-layout` JSON, or LDML `<layers formId="touch">` the keyboard actually ships (§4) — and explicitly check whether a real custom touch layout exists at all before trusting it, given the documented US-English-QWERTY-touch-layout fallback (§2). Build a separate touch-specific keystroke-adjacency prior from this; do not conflate it with the hardware graph, since Keyman's own architecture never does.
   - **No off-the-shelf Keyman tool produces either graph today** (§5) — this is new tooling PanGloss would build, most naturally as a small offline analyzer in the spirit of Keyman's own existing `kmc analyze osk-char-use` precedent, consuming the openly-documented `.kmx`/`KMX+`/LDML formats directly (all specified in the MIT-licensed `keymanapp/keyman` repo), or alternatively by exhaustively driving Keyman Core's stateless (but not publicly-contracted-for-this-purpose) Processor API. Either is buildable against primary, redistributable specifications; neither currently exists as a published library.
   - **Target LDML `keyboard3`, not KMX, as the long-term parse target**, since Keyman itself is consolidating on it for exactly the fragmentation reasons that matter most to SIL's own field-language mission (§6) — but budget for `.kmx` support too, since most currently-deployed field keyboards, especially on the mobile/web platforms most field typists actually use, are `.kmn`/`.kmx`-only as of this research (LDML mobile/web support still in development).
   - **When no installed keyboard artifact is available at all** (e.g., a grammar with no associated Keyman keyboard yet, or before this tooling exists) — the fallback should be an honestly-labeled generic QWERTY/AZERTY prior of last resort, not silently promoted to "the" model. This matches Aspell's own supported `keyboard=none` mode (§1): a documented, users-know-it's-happening opt-out, not a hidden default.

5. **Flag, don't hide, the sources this report could not independently verify**: Kernighan/Church/Gale 1990 and Brill & Moore 2000's primary PDFs, Goodman et al.'s original touch-model paper, and Google's FST mobile-keyboard-decoding paper's full text were all either unreachable or returned undecodable binary content in this environment; all four are corroborated only via consistent secondary/abstract-level characterization (ACL Anthology, ACM DL, dblp, Semantic Scholar, or search-result summaries), not independently read cover-to-cover. Divvunspell's ERRORSOURCE-authoring process (specifically, whether it is itself keyboard-derived) was searched for and not found. Aspell's `.kbd` file's exact internal syntax was likewise not independently confirmed beyond secondary characterization. These are exactly the kind of claims that should be re-verified (e.g., via a proper PDF-text-extraction tool, or by reading the actual `.kbd`/ERRORSOURCE source files rather than documentation about them) before being load-bearing for an implementation decision, per report 02's own established practice of flagging unfetchable sources rather than silently asserting them.
