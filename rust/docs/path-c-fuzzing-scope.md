# Path C — differential fuzzing: scoping note (P9(c), not built)

Status: **scoping only**, per this task's own tag (`[SONNET; fuzzing harness design OPUS]` on
`rust-optimizations-phase2.md` §P9). No harness code, no generator, no design decisions locked in
here — this is the brief for the Opus-tier agent who designs and builds it. Written so that agent
can start immediately without re-deriving the mechanical context below; the open questions in §5
are the actual design work and are deliberately left unanswered.

## 0. Why this exists (recap from the plan)

`rust-optimizations-phase2.md` §Feeder path C: "Generator that produces/mutates small grammars
(toggle DTD attributes, permute rule order, inject rarely-used constructs, vary feature systems
incl. zero-feature tables) + short word lists; run both engines; ANY normalized-output diff is a
finding — minimize (delta-debug the grammar down), classify (Rust bug vs undocumented C# nuance),
and freeze as a permanent fixture either way. Seeded RNG for reproducibility; corpus of minimized
fixtures grows monotonically. Run bounded batches (e.g. 500 grammars/run) rather than open-ended;
CPU-heavy, so schedule when no benchmark/baseline is running."

Everything else in this document either (a) reports mechanical facts this P9 pass verified directly
(what tools exist, what they output, how they're invoked), or (b) lists a decision Opus needs to
make, explicitly flagged as such. Nothing below should be read as a recommendation unless labeled
one.

## 1. What a generator needs to produce — two independent mutation surfaces

**Both grammar mutation AND word mutation are needed; they test different things and should vary
independently (cross product, not either/or):**

- **Grammar mutations** exercise different C# code paths (which rule types, which DTD attributes,
  which feature-system shapes) — this is what actually varies *branch coverage* (the gate-5 metric
  this same task's part (b) measured). A generator that only mutates words against a fixed grammar
  will keep hammering the same branches.
- **Word mutations** (against a fixed grammar) exercise the *search space* for a given rule set —
  this is where the P10 (StrRep identity) and the row-1/row-3 (merge/split narrowing) findings this
  session actually came from: same grammar, different surface strings, different FSA paths taken.
  Both of those were found by humans hand-writing probe words for a hand-written probe grammar —
  Path C automates exactly that pattern.

### 1.1 Grammar mutation — concrete substrate already in the repo

The DTD (`.worktrees/parse-opt/src/SIL.Machine.Morphology.HermitCrab/HermitCrabInput.dtd`, 618
lines) is the ground-truth schema. Every `rust/conformance/*/*/grammar.xml` fixture (34 as of this
session) is a small, hand-authored, DTD-valid grammar — these are natural **seed corpus** members
for a mutator (real, minimal, already-proven-loadable-by-both-engines grammars, covering most DTD
constructs already: rewrite rules, affix rules, compounding, realizational rules, co-occurrence
rules, MPR groups, pattern-shape allomorphs, metathesis).

Two structurally different ways to mutate an XML grammar, with different cost/validity trade-offs
(Opus must pick, see §5.1):
- **Text/DOM-level mutation**: parse with any XML tree library (quick-xml, already a workspace
  dependency via `pg-grammar`), do tree-shape edits (swap attribute values from the DTD's own
  enumerated value lists, e.g. `morphologicalRuleOrder="unordered"` ↔ `"linear"`; duplicate/reorder
  child elements; toggle optional attributes on/off), re-serialize. Cheap to build, but produces
  more DTD-invalid or nonsensical grammars that both engines will reject identically (a "finding"
  that isn't one — wasted cycles, needs a fast pre-filter).
- **Typed-AST mutation**: `pg-grammar`'s loader (`rust/crates/pg-grammar/src/load.rs`) already
  parses XML into a typed `Grammar`/`*Def` model — this is the natural mutation substrate (mutate
  the typed tree, which can enforce structural invariants the DTD implies, e.g. "every
  `naturalClass` attribute value must reference a declared `NaturalClass` id"). **Gap found this
  session: there is no XML writer/serializer anywhere in `pg-grammar`** (`grep` for
  `write|Writer|to_xml|serialize` in `crates/pg-grammar/src/` returns nothing) — C# has
  `XmlLanguageWriter` (94% branch-covered per this task's part (b) measurement, so a well-exercised
  reference implementation exists) but Rust has never needed one, since the port only ever
  *consumes* grammars. Building one is real, scoped work Opus should size explicitly, not assume.

### 1.2 Word mutation — cheap, no new tooling needed

Given a grammar (mutated or not), words can be generated by:
- sampling `CharacterDefinitionTable` segment representations directly (every fixture's `grammar.xml`
  declares its own alphabet — trivially enumerable from the loaded `Grammar`), producing random
  strings over that alphabet at varying lengths;
- mutating existing `words.txt` corpus/fixture words (single-char substitution/insertion/deletion,
  the classic fuzzing move) — cheap and already known to find real divergences (this is close to
  what a human did by hand to build e.g. `rewrite/merge`'s 3-word probe list).

This half needs no new infrastructure beyond a small standalone script/crate; the harder half is
§1.1.

## 2. Differential comparison mechanics — already straightforward, established this session

Both engines are already CLI-invokable per-fixture, exactly as every `rust/conformance/*/*/`
README documents:

```
# C# oracle
DOTNET_gcServer=0 dotnet <parse-opt>/SIL.Machine.Morphology.HermitCrab.Tool/bin/Release/net10.0/hc.dll \
  -i grammar.xml -s <script with: batch words.txt out_csharp.tsv>

# Rust
pangloss.exe batch grammar.xml words.txt out_rust.tsv --step-cap=<N>
```

Normalization (established convention, used verbatim across every fixture's README this session
audited): both engines emit a 5-column TSV (`idx, word, ms, status, sig`); drop interleaved
`STARTED` lines (`NF==5` filter), compare on `word, status, sig`:
```
awk -F'\t' 'NF==5 {print $2"\t"$4"\t"$5}' <file> | sort
```
`diff` (or an in-harness line-set comparison) on the two normalized streams — any non-empty diff is
a finding. This mechanical piece needs no design work; a harness can lift it directly.

One live wrinkle to build in from day one, found by this same P9 pass (not hypothetical): the C#
oracle itself is not always self-consistent (`rewrite/expand`'s README documents `hc.dll`'s
`tracing on`/interactive `parse` accepting a word that the untraced `batch` command rejects, same
grammar, same word, same oracle binary). A harness that always invokes `batch` (as the plan
specifies) will not hit this itself, but should be aware that "the oracle disagrees with itself
depending on invocation mode" is a real, already-observed category of non-finding-shaped noise.

## 3. What "any normalized diff, minimized, frozen as a fixture" means concretely

**Minimization is two independent shrink axes, both needed:**
1. **Grammar shrink**: remove rules/classes/features/lexical entries from the diff-producing
   grammar while the diff (on some word) still reproduces. Classic delta-debugging (ddmin):
   binary-search over "chunks" of the typed AST (whole `<MorphologicalRule>`, whole
   `<NaturalClass>`, etc. — coarse structural units, not byte-level XML text, to stay DTD-valid
   throughout the shrink) removed and re-tested for divergence persistence.
2. **Word shrink**: shorten/simplify the triggering word (same ddmin idea, at the character level)
   against the now-small grammar, keeping the diff alive.

Freezing = writing the shrunk `(grammar.xml, words.txt)` pair into
`rust/conformance/<new-area>/<name>/` with an oracle-generated `expected.tsv` and a README
documenting the diff, following the exact established pattern this session audited 34 instances of.
**One open question this raises that Opus must resolve, not this doc:** today's fixture convention
has exactly two shapes — MATCHES (fixture asserted equal, wired as a passing test) and DIVERGES
(fixture frozen, documented, *not* wired as a passing test, e.g. `rewrite/merge` before this P9
pass, or `rewrite/expand` after it). Path C findings will be DIVERGES by construction (a diff is
the definition of a finding) — does every fuzz-found divergence get a fixture, unconditionally
(monotonic corpus growth per the plan), or only after triage confirms it's a genuine Rust gap and
not oracle noise (§4)? That ordering matters for whether triage happens before or after freezing.

## 4. Decisions an Opus-tier designer needs to make — not guessed at here

These are real judgment calls with no obviously-correct default; each has a plausible case both
ways, which is exactly why this task's own tag routes the *design* to Opus while leaving the
mechanical plumbing (§1-§3 above) as something a Sonnet-tier implementer can execute mechanically
once the design below is fixed:

1. **Text/DOM mutation vs. typed-AST mutation (+ building a writer)** (§1.1). Cost/benefit: DOM
   mutation is buildable in a day but wastes most cycles on DTD-invalid or semantically-void
   grammars (both engines correctly reject them identically — not a finding); typed-AST mutation
   needs a new XML writer (real, unscoped-here effort) but produces a much higher finding-rate per
   grammar generated. No measurement exists yet of the DOM-mutation reject rate to make this
   trade-off quantitatively — that measurement itself could be a cheap first Opus deliverable
   before committing to a writer-building effort.
2. **Mutation weighting / DTD-construct coverage policy.** Which rule types, attributes, and
   feature-system shapes get mutated with what relative frequency. Naive uniform-random mutation
   over the DTD's ~30 element types will spend most of its budget on well-trodden paths (simple
   affix/rewrite rules) that this session's HISTORY-MATRIX pass just finished proving are mostly
   `covered`. A coverage-guided weighting (bias toward the "top uncovered classes" table in this
   task's part (b) deliverable, `rust/parity-out/audit/phase2/coverage/COVERAGE-GATE5.md` —
   `SynthesisCompoundingRule`, `SynthesisRealizationalAffixProcessRule`,
   `SynthesisRewriteRule`, `AllomorphEnvironment`, `MorphCoOccurrenceRule<T>`) would likely be far
   more efficient, but "likely" isn't a design — Opus should decide whether/how to wire the
   coverage report into the mutation weighting, versus treating it as a one-time human-read hint.
3. **Exclusion list for known non-goals.** The root-guesser subsystem (`GuessRoot`/`LexicalGuess`)
   has zero Rust surface at all (reconfirmed this session, HISTORY-MATRIX rows 12-18/25/etc.) —
   fuzzing grammars/paths that only exercise the guesser will produce "findings" that are just
   "feature doesn't exist," not new information. Does the mutator need to actively avoid guesser-
   triggering constructs (there may not even be a DTD-visible way to invoke it — it's a `Morpher`
   API flag, `guessRoot`, not a grammar-XML construct, so this may be moot — Opus should verify),
   or is a coarse post-hoc filter ("diff only in guesser-related code paths → discard") good enough,
   and if so, how would that filter be implemented (coverage-diff on the C# side per fuzz case is
   one option, expensive per-case; a static allowlist of grammar constructs is cheaper but coarser).
4. **Classification policy: Rust bug vs. C# self-inconsistency vs. undocumented nuance.** This
   session found a live example of the middle category (`rewrite/expand`'s traced-vs-untraced
   divergence) *without* fuzzing — a fuzzer running only `batch` won't hit that specific case, but
   will very likely hit its cousins (timing-sensitive, thread-count-sensitive, or determinism-
   sensitive oracle behaviors — C#'s own `GenerateWords`/parallel-synthesis history, rows 52-53 in
   HISTORY-MATRIX, shows the C# side itself has had real thread-safety bugs). A fully-automatic
   classifier isn't realistic; what's needed is a **triage protocol**: does every fuzz-found diff
   get a human read before freezing (bounded batches, per the plan's "500 grammars/run," make this
   tractable), or does the harness auto-freeze everything and rely on periodic human sweeps of the
   growing corpus? This determines whether the harness is "fire and forget nightly" or
   "produces a reviewable batch."
5. **Determinism / reproducibility contract.** The plan specifies "seeded RNG." Needs a concrete
   decision on: the seed format/CLI surface (a single u64? a seed file capturing grammar-gen +
   word-gen streams separately for independent replay?); whether both engines are forced
   single-threaded (`--sequential` on `pangloss`/`hc.dll`, both already support this flag) to eliminate
   a whole class of non-reproducible non-findings (C#'s own historical `ConcurrentQueue`/thread-
   safety commits, rows 52-53, suggest parallel-mode nondeterminism is a real risk here, not
   theoretical); and how a "replay this exact fuzz run" command is exposed for debugging a harness
   bug versus a genuine finding.
6. **Runaway-case containment.** Sena real words are known (this session's own V2/P10 work) to
   explode to hundreds of thousands of FST steps on certain shapes; a generator producing novel
   grammar/word combinations WILL find pathological cases. Both CLIs already support `--step-cap`
   and `--word-timeout-ms` (Rust) / presumably need an equivalent bound on the C# side (check
   `BatchCommand.cs` for an existing timeout knob before assuming one needs building) — Opus needs
   to set the actual bound values and decide whether a case that hits the cap on ONE engine but not
   the other counts as a "finding" (a capped-vs-uncapped STATUS_DIFF, which this session's V2 Sena
   work already showed is a real, frequent, non-bug category — 112/7121 Sena words were exactly
   this shape) or gets filtered out before comparison.
7. **Corpus growth / dedup policy.** "Corpus of minimized fixtures grows monotonically" (the plan's
   words) — but a fuzzer re-discovering minor variants of the same root cause (e.g. a dozen
   different words all hitting the exact `merge`-family narrowing gap this session's row-1/row-3
   audit just closed/re-opened) will bloat the conformance suite with near-duplicate fixtures that
   all break together and fix together. Needs a dedup key — plausibly "which C# method/branch does
   the diff trace through" (ties back to the coverage tooling in part (b) of this task — the same
   `dotnet-coverage` instrumentation used for the gate-5 number could, in principle, fingerprint
   which branches a given fuzz case exercises, and two cases with identical exercised-branch-sets on
   the diverging path would be considered duplicates) — but that's a real design, not a given; a
   cheaper first cut (dedup on grammar-shape signature, or normalized-diff text) is also plausible
   and much easier to build. Opus should pick one deliberately, not by default.
8. **Where the harness lives and its performance budget.** A new crate under `rust/crates/`? A
   standalone script (PowerShell, given this repo's Windows-primary tooling, or a small Rust
   binary calling out to both CLIs via `std::process::Command`)? Scheduling: the plan explicitly
   says "never concurrent with a benchmark/baseline run" (this session itself operated under that
   exact constraint, sharing the machine with a live multi-hour Sena benchmark in a sibling
   worktree) — does the harness need its own lockfile/coordination mechanism with other
   long-running repo work, or is manual scheduling (a human/agent checks before kicking off a
   fuzzing batch) sufficient given the "500 grammars/run" bounded-batch framing?
